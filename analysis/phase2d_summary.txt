Phase 2d: Complete Field Descriptor Architecture Summary
========================================================

Date: 2026-10-20 (Updated)
Binary: WINPROJ.EXE (PE32+, image base 0x140000000)

ARCHITECTURE OVERVIEW
=====================

MS Project's field system has three layers:

1. COM Layer (IBkndTaskDispatch)
   - External callers use field IDs (PjField enum values, e.g. pjTaskDuration)
   - COM dispatch routes through FUN_1403cff50 -> TBkndElem -> TTaskTable

2. Scheduling Engine Layer (TTaskTable)
   - TTaskTable::vfunc[87] is the high-level GetFieldValue
   - TTaskTable::vfunc[158] is the bottom of the chain
   - Uses PropInfoData objects at 0xA8-byte stride (see CACHE STRIDE BREAKTHROUGH)

3. Record Layer (TASKNODE/RSCNODE/ASSNNODE)
   - In-memory structs with type-specific slot arrays
   - PropInfoData +0x18 = slot index within the type-specific array
   - Getter function pointers in the 0x68-byte tail dispatch to actual record data

CACHE STRIDE BREAKTHROUGH
=========================

*** The cache entry stride is 0xA8 (168 bytes), NOT 0x40 (64 bytes) ***

Each 0xA8-byte "slot" consists of:
  - 0x40 bytes: PropInfoData object (vtable + field metadata)
  - 0x68 bytes: Auxiliary data (getter/setter ptrs, related field IDs, index)

Using cache_base + index * 0xA8 yields 100% of all 3,207 entries.

Previous assumption (0x40 stride) only found ~5% of entries due to
interleaved auxiliary data being misinterpreted as "garbage".

DUAL-STRIDE ADDRESSING IN VFUNC[158]
=====================================

The function at RVA 0x239380 uses TWO different strides:

1. SHL RDX, 6 (at RVA 0x23955C): index * 0x40
   - Used with R13 (4th parameter = cache pointer from caller)
   - Reads type_code at [R13 + index*64 + 0x0C]
   - Quick-access path for type validation

2. IMUL R14, RCX, 0x78 (at RVA 0x23957D): index * 0x78 (120)
   - Used with this->member_0x58 (saved at [RBP+0x28] in prologue)
   - Indexes into secondary data structure
   - May contain the actual TASKNODE record access functions

Prologue (RVA 0x239380):
  R13 = R9 (4th parameter = cache base passed by caller)
  [RBP+0x28] = this->field_at_0x58
  EBX = EDX = field_id (2nd parameter)
  R14D = R8D (3rd parameter)

Relationship: 0x40 + 0x68 = 0xA8 (total stride), but the secondary
stride is 0x78 (not 0x68). The exact mapping between the three strides
(0x40, 0x68/0xA8, 0x78) requires deeper analysis of the caller.

RECORD OFFSET = SLOT INDEX (NOT BYTE OFFSET)
=============================================

The record_offset field (+0x18 in PropInfoData) is a SLOT INDEX within a
type-specific sub-array, NOT a direct byte offset into the record struct.

Multiple fields share the same (type, offset):
  Type 5, offset 8:  Work, BaselineWork, ActualWork, WorkVariance, etc. (71 Task fields)
  Type 5, offset 9:  Cost, BaselineCost, ActualCost, FixedCost, etc. (92 Task fields)
  Type 8, offset 21: Name, WBS, Text1-30, Subproject, etc. (311 Task fields)
  Type 11, offset 17: Critical, Milestone, Flag1-20, etc. (229 Task fields)
  Type 19, offset 4:  Start, EarlyStart, LateStart, etc. (126 Task fields)
  Type 19, offset 27: Finish, EarlyFinish, LateFinish, etc. (46 Task fields)

The FLAGS field (at +0x1C) distinguishes individual fields within a group:
  - Baseline number (0-10)
  - Actual/remaining/variance/computed mode
  - Enterprise vs standard
  - Read/write permissions

The getter function (code pointer in 0x68-byte tail at +0x58) uses the
field_id + flags to compute the actual value from the record data.

AUXILIARY TAIL DATA (bytes 0x40-0xA7 of each entry)
===================================================

Each entry's 0x68-byte tail contains:
  +0x58: Code pointer (getter function, in .text ~RVA 0x4b43a0 or 0x7de620)
  +0x60: Related field_id (e.g., text representation of current field)
  +0x68: Code pointer (common accessor, in .text ~RVA 0x7ddf30)
  +0x90: Data pointer (RVA ~0xf6b768, consistent per record type)
  +0x98: Code pointer (RVA ~0x7ddd60, consistent per record type)
  +0xA0: Entry index (0, 1, 2, ...)
