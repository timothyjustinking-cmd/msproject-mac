# memory/e5.md — Project's stored late pair for a manual row (wave 20)

Read `docs/handoff/e5.md` for the evidence table. Short version for anyone
touching `+112/+116`, manual rows, the plan bridge or the scenario applier.

## Durable facts

* **A manual row's stored late pair is `the row placed at its latest`.**
  `late finish = min(project finish, each successor's KEPT start − lag)` and
  `late start = max(kept start, sub_work(late finish, Duration))`. The FS/FF
  subtraction and the duration walk are the **plain** calendar walk; do NOT
  `align_back` the predecessor bound the way an auto row's CPM late finish is
  aligned (that produced 01-09 12:00 where Project stores 01-09 13:00).
* **It is not the CPM pair and not the kept pair.** recalculate stores
  01-06 13:00 / 01-09 12:00 for uid 2 whose kept dates are 01-04 13:00 /
  01-07 12:00; delete-task-with-successor stores 01-09 13:00 / 01-16 12:00 for
  uid 1. The clamp `max(kept start, …)` is load-bearing (link-fs-lag uid 1,
  w12-linkadd uid 1/2, duration-change uid 1/2).
* **The successor bound reads the successor's EARLY/KEPT date, not its late
  date.** PROJECT_B uid 10775 stores 08-26 08:00 (= successor 10776 kept start);
  10776's late start is 09-10 08:00.
* **SS/SF links do not bound LF** (w12-linkadd uid 1's SS+1d link leaves LF at
  the FS bound); FF is inferred (no measured manual FF row).
* **Slack words are unchanged** by this rule: they stay the effective pass's
  values (TotalSlack = LF−EF, StartSlack = TotalSlack); the stored pair's
  difference from the CPM pair is usually the (zero-working-time) lunch break.
* **Auto rows are untouched.** The computation lives in `core/plan` after the
  results are built, gated on `PlanTaskResult::manually_pinned`; the CPM
  definitions (`core/sched/cpm.cpp`) were not modified.

## Where it lives

* `core/plan/plan.h` — `MANUAL LATE PAIR` header section + `manually_pinned` +
  `PlanResult::manual_late_unmodelled`.
* `core/plan/plan.cpp` — the second pass inside `recalculate()` (search
  "MANUAL LATE PAIR").
* `tests/engine_diff_tests.cpp` — the applier writes the plan's pair for a
  pinned manual row (it used to keep the stored pair); each built-in case pins
  its exact pair.
* `tests/plan_recalc_tests.cpp` — `test_manual_late_pair` (the four scenarios +
  the auto control).

## Traps

* The applier saves twice per scenario; the rule is idempotent because it reads
  only kept dates/durations (both passes are modelled in the plan test).
* An unpinned manual row (no stored start, elapsed duration, actuals) has no
  measured rule: it keeps the CPM pair and increments `manual_late_unmodelled`
  if the walk could not be modelled (elapsed lag / overflow).
* Dropbox mtime churn makes `edit` fail right after a read; re-read and retry.
