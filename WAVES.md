# Coordination board

Owner: the coordinator (the long-running chat). Agents do not edit this file —
they report on their branch and in their end-of-run message.

## How work is organised

Each wave is a set of **non-overlapping streams**. Every stream gets its own git
branch and its own worktree, so four agents can run at once without touching each
other's files or each other's index.

```
main                       merged, always working
wave<N>/<stream>           one branch per agent, pushed, merged by the coordinator
D:\dev\wt\<stream>         the worktree that agent works in
```

Merging: the coordinator reviews, merges `--no-ff` into `main`, runs the
verification commands the stream recorded, then pushes. **Agents never merge and
never push to `main`.**

## Correction to the wave 1 findings (2026-10-22)

Wave 1's headline claim — that the .mpp keys variable data by its own field-key
namespace rather than by COM PjField ids — is **false**, and is withdrawn.

W5 found it by rebuilding the parser: VarMeta has a **24-byte** header (not 32) and
12-byte entries of **(uid, offset, key)**. Wave 1 started the entries 8 bytes late and
read the triple as (key, uid, offset), pairing every field with the *next* entry's
uid and offset. That is where "Task.Name = 0x0b400564" came from.

Verified independently by the coordinator:
- PROJECT_A entry 2: uid=0, offset=24, key=0x0b40000e -> Var2Data[24] = "Project A".
- base.mpp entry 0: uid=0, offset=76, key=0x0b40000e -> "base" (the project name).

Consequences:
1. `analysis/field_id_map.tsv` **does** decode the file. Name = 0x0b40000e, Notes = 0x0b40000f.
2. PROJECT_A VarMeta actually holds 1,081 entries (header says 1076) — wave 1 said 1,080.
3. The reader built on the old parse was reading Var2Data at wrong offsets, which is the
   most likely cause of the aborting test.

`data/field_keys.tsv` now names 185 Task keys: 2 proven, 138 high confidence
(cross-checked against the PjField tables and mpxj), 12 medium, 33 structurally
described but unnamed. Coverage on PROJECT_A: 61.5% of entries, 82.3% of distinct keys,
71.7% of addressed bytes.
