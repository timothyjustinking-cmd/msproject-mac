## 3. MPP12 differs from MPP14 — measured, with evidence

Everything here is measured on the fixtures above unless marked
**[inference]**. The byte tables are also in `core/mpp/reader.cpp`, section
"MPP12".

### 3.1 Container and version

| | MPP12 | MPP14 |
|---|---|---|
| top-level props | `Props12`, version key `0x3540000c` = UTF-16 `12,0,4017,1004` (mpp12resource: `12,0,6423,1000`) | `Props14`, `16,0,20430,20182` for a Project-16 file |
| engine tables | `112/` | `114/` |
| view state | `212/` | `214/` |
| tables present | Task, Rsc, Cons, Assn, Cal, OutlCode | same + Attachment / ChecklistItem / Conversation / Label / LabelAssociation (empty), Sprint/BoardColumn in some files |
| view documents | CEdl, CFilter, CGrouping, CMap, CReport, CTable, CUdm, CV_iew, CCommandBar | CDrawing, CEdl, CFilter, CGrouping, CMap, CReport, CTable, CV_iew, CVba |

Detection is in `detect_format()` and never assumes a root: `Props12` vs
`Props14` decides, the storage that actually holds `TBkndTask/FixedData` is the
fallback and the tie-breaker, and a disagreement is a warning. No numeric
version word is trusted.

### 3.2 Table geometry

| table | MPP12 | MPP14 |
|---|---|---|
| `TBkndTask/FixedData` | 48-byte header + 264 B rows | 48 + 202 |
| `TBkndTask/FixedMeta` | 16 + 47·(rows+3) (same stride) | same |
| `TBkndRsc` | 48 + 188 | 48 + 172 |
| `TBkndCons` | 20·rows, no header | same |
| `TBkndAssn` | 142·rows, no header | 110·rows |
| `TBkndCal` | 64 + 12·rows | same |
| Task `Fixed2Data` / `Fixed2Meta` | 176·rows (16+86 per entry) | 64·rows (16+96) |
| Resource `Fixed2Meta` | 16 + 49·(rows+3) | 16 + 51·(rows+3) |
| VarMeta / Var2Data | 24-byte header + 12-byte (uid, offset, key); length-prefixed blocks — **unchanged** | same |

Why 264 is a measurement and not a guess: `mpp12task`'s Task FixedMeta
offsets are `0,16,32,48,312`, its FixedData is 576 B, and 576 = 48 + 264·2;
`mpp12relations` is 1632 = 48 + 264·6; every other fixture divides exactly.
Rows are read **by FixedMeta entry offset** (the next entry bounds each row),
because MPP12 interleaves 16-byte "null-task" blocks: `mpp12nulltasks` offsets
are `48,312,576,592,856,1120,1136,1400,1416` with sizes
`264,264,16,264,264,16,264,16,264`. A 16-byte block has FixedMeta state 0x04
and no VarMeta group; it is not a task. A row whose size is neither 16 nor 264
is refused with a warning that names the row (never guessed).

### 3.3 MPP12 task fixed row (264 bytes)

```
+0   u32 UniqueID          +4   u32 ID            (REVERSED vs MPP14!)
+8   u32 EarlyFinish       +12  u32 LateStart
+16  u32 Stop              +20  u32 Resume
+24  i32 FreeSlack         +28  i32 StartSlack    +32 i32 FinishSlack
+36  u32 parent UniqueID (0xffffffff on the project row; 0 = project row)
+40  u16 OutlineLevel (STORED)
+58  u16 unused (0 in every row)
+60  u32 Duration (ticks)  +64 u16 DurationFormat (PjFormatUnit + 0x20 est.)
+66  u32 ActualDuration    +70 u32 RemainingDuration  +74 u32 BaselineDuration
+80  u16 ConstraintType    +88 u32 Start  +92 u32 Finish  (effective pair)
+96  u32 ActualStart       +100 u32 ActualFinish
+104 u32 BaselineStart     +108 u32 BaselineFinish
+112 u32 ConstraintDate    +116 u32 ResumeNoEarlierThan
+120 u16 Priority          +122 u16 PercentComplete
+126 u16 Type              +128 u16 FixedCostAccrual   +130 u32 Created
+136 u32 PreleveledStart   +140 u32 PreleveledFinish
+148 u32 EarlyStart        +152 u32 LateFinish
+156 u32 SummaryProgress   +160 i32 CalendarUniqueID (-1 = none)
+164 u32 Deadline
+168 f64 Work (minutes×1000) ... +200 f64 Cost (hundredths) ...
```

Proof of the reversed uid/ID: `mpp12resource` first task has uid **2** / ID
**1**; `mpp12viewstate` first task uid **5** / ID **1**; `mpp12calendar` uid 2 /
ID 1. Reading +0 as ID would number the tasks 2,3,4 and lose the dense 1..n ID
sequence Project's own tests assert.

`DurationFormat` proof: `mpp12duration`'s ten tasks are 1 min / 1 h / 1 d /
1 wk / 1 mo and the elapsed variants; +64 reads 3,5,7,9,11 and 4,6,8,10,12 with
durations 10, 600, 4800, 24000, 96000 and 10, 600, 14400, 100800, 432000 ticks.
The word at +58 is 0 in every row of every fixture, so the MPP14 name
"actual duration units" is misleading: +64 is the duration's display unit.

There is **no calculated Start/Finish pair** in MPP12 (+96/+100 are the
actuals). `Task::calculated_start/finish` are set equal to the effective pair
and `Task::start_anchor` stays `kDateNa` (no measured equivalent).

### 3.4 Resource row (188 bytes) and Resource Type

`uid +0`, `ID +4`, `MaxUnits` f64 `+44` (x100: 10000.0 = 100 %). Type:
`FixedMeta` entry `+9` bit 0x02 = Work; when clear, `Fixed2Meta` entry `+8`
bit 0x10 = Cost, else Material. Measured on
`resource-type-project2007-mpp12.mpp`: the five rows named "Cost Resource N"
have fm+9 = 0x20 and f2+8 = 0x83 (bit set), the five "Material Resource N"
have 0x20 / 0x43, the five "Work Resource N" have 0x32 (bit set). Name /
Initials / MaterialLabel are the same VarMeta keys as MPP14.

### 3.5 Link row (20 bytes) — lag and format are swapped

`uid +0, pred +4, succ +8, type u16 +12, LagFormat u16 +14, lag i32 +16`.
MPP14 has lag i32 at +14 and format u16 at +18. Evidence:
`mpp12relations` is 1→2 FS, 2→3 SS+1d, 3→4 FF, 4→5 SF (MPXJ's
`MppTaskTest.testRelations` asserts exactly those); the SS row stores
+14 = 7 (days) and +16 = 4800 ticks (1 day). Reading +14 as lag would give
1,228,807 ticks. Link liveness is FixedMeta coverage + state, as in MPP14.

### 3.6 Assignment row (142 bytes)

`uid +0, task uid +4, resource uid +8 (0xffff0001 = none), Start +12,
Finish +16, Units f64 +54 (x100), Work f64 +62 (minutes×1000)`.
On `mpp12resource` all 5 assignment Start/Finish pairs equal their task's
effective pair, and `mpp12duration`'s two unassigned rows store 0xffff0001.
MPP12 stores **no Resume/Stop date** for an assignment (the field is absent
from the row), so `Assignment::resume` stays `kDateNa`.

### 3.7 Metadata bits: milestone, flags, liveness

| fact | MPP12 | MPP14 |
|---|---|---|
| Milestone | FixedMeta entry `+8` bit 0x20 | `+10` bit 0x02 |
| Flag1..Flag20 | contiguous bit field from entry `+37` bit 0x20 through `+40` bit 0x01 | Flag1 only, `+24` bit 0x02 |
| descriptor entries | 3 × 16 B, state 0x04 | 3 × 16 B |
| row state | +0: 0x00 live, 0x02 tombstone, 0x04 null/descriptor | +0: 0x00/0x02 |
| manual scheduling | does not exist (Project 2007) | Fixed2Meta +8 bit 0x80 |

Milestone evidence: `mpp12task` Task #1 stores +8 = 0x63 (0x20 set) and MPXJ's
`MppTaskTest.testBasicTask` asserts `getMilestone()` for it despite its 5-day
duration; `task-flags-project2007-mpp12`'s 20 flag rows store +8 = 0x43 (clear).
Flags evidence: that same fixture names its tasks "Flag1".."Flag20"; each named
task sets exactly the expected bit (Flag1 byte 37/0x20, Flag2 0x40, Flag3 0x80,
Flag4 byte 38/0x01, … Flag20 byte 40/0x01). All twenty are therefore decoded
for MPP12; the reader still exposes only Flag1 for MPP14.

### 3.8 Outline: stored, not derived

MPP12 stores parent uid at +36 and OutlineLevel at +40. On
`mpp12recurring` the eight summaries are level 1 with parent 0 and their
children level 2 with the summary's uid, across uid gaps (uids 1,4,10,16,22,28,
34 — recurring child rows consume their own ids). `mpp12nulltasks` gives a
second check (1 / 1.1 / 1.2 / 2 / 2.1). The reader uses the stored level
(a mismatch with the parent chain is warned about) and derives
OutlineNumber from the parent links; `Summary = child_count > 0`.

### 3.9 Calendars — same size, different column order

Both formats: `FixedData` = 64 + 12·rows, names in VarMeta key 0x0d400001.
MPP12 row = (calendar uid, base uid, resource uid); MPP14 = (base uid,
resource uid, calendar uid). Evidence: MPXJ's
`MPP12CalendarFactory.getCalendarIDOffset()=0 / getBaseIDOffset()=4 /
getResourceIDOffset()=8` (the MPP14 factory puts the calendar id at +8); and
`mpp12task` rows `(1,-1,-1),(2,1,0),(3,1,1)` name calendar 1 "Standard" while
`base.mpp` rows `(0,-1,1),(1,0,2),(1,1,3)` name 1,2,3.

### 3.10 Master/subproject

An inserted project is an ordinary task row plus:

* Task VarMeta key **0x0b4001ca** (field id 458,
  `PjTaskSubprojectTasksUniqueIDOffset`): a u32 base added to the subproject's
  ids. `mpp12subproject`: uid 2 = 0x00800000 (8388608), uid 3 = 0x00c00000
  (12582912). MPXJ's `MppSubprojectTest` asserts 8388608 for uid 2.
* The project props' `SUBPROJECT_DATA` record (`112/Props` key `0x024000a2`,
  plus a count at `0x02400084`). Layout: header (block size, unknown, u32 item
  table offset), then a list of u32 item-header offsets masked with 0x1FFFF.
  An item header is 16 bytes GUID + 4 flag bytes; the **type byte is at
  header+16**. For type 0x01/0x08 the following three u32 give the uid list
  offset, the path offset and a file-name offset. The path is a nested block:
  +18 u32 DOS-string length, ASCII DOS path (NUL-terminated), +24 u32 nested
  block size (0 = no Unicode copy), u32 UTF-16 byte length, 2 bytes, UTF-16
  path. `mpp12subproject` decodes uid 2 → `D:\java\mpxj\junit\data\
  SubprojectA-9.mpp` and uid 3 → `…\SubprojectB-9.mpp`; both records are
  reported in `Document::subprojects` and on the task as
  `Task::subproject_file`.

The master stores the summary row only: the subproject's own tasks are in the
subproject file, not this document. MPXJ's test also checks the "read-only"
flag on the inserted project; no byte for it has been located, so it is not
exposed.

### 3.11 `112/Props` / `212/Props`

Both are the same Props12 block format as the top-level `Props12` (16-byte
header, u16 count at +12, `(u32 length, u32 key, u32 unused, data)` padded to
even). `112/Props` has 212 records and carries the project title/company,
currency, default calendar name, and the subproject table. The reader parses
it only for SUBPROJECT_DATA; everything else in it is deliberately opaque.
`212/Props` and the `212/` view documents are opaque (view state is not read,
as for MPP14's `214/`).

### 3.12 Remaining variant: MPXJ-written MPP12 (`*-from14.mpp`)

The MPXJ test corpus also ships `mpp12subproject-from14.mpp` (and similar
`-from14` files): MPP12 *framing* (`Props12`, `112/`, `212/`) written by
MPXJ's own writer rather than by Project. Its task records are **206 bytes**
(`mpp12subproject-from14`: FixedMeta offsets `0,16,32,48,254,460,666`, FD 872),
not Project 2007's 264 — and +60 does not hold a tick duration there
(524288). This is a different record layout, not a shifted one. The reader
refuses it explicitly: if every data row of the Task table has an unsupported
size it throws
"MPP12 Task table at 112/TBkndTask/FixedData holds 3 data rows of 206 bytes
each (row 0 is the project row); the Project-2007 layout this reader implements
is 264 bytes…", instead of returning a project with no tasks. A Project 2007
file with no tasks has only the project row and does not trip this rule
(`mpp12header` loads as 0 tasks). The corpus sweep skips `*-from14.mpp` for
that reason and `test_mpp12` pins the refusal (both sizes named in the error).

## 4. Password-to-modify / read-only — what the file stores

The top-level props block (Props12 or Props14, same layout) stores:

| key | meaning | type |
|---|---|---|
| `0x35400000` | `PASSWORD_FLAG`: 0x00 none, 0x01 read password, 0x02 write reservation, 0x03 both | 1 byte |
| `0x35400004` | read-protection password hash | bytes (present/absent) |
| `0x35400005` | write-reservation password hash | bytes (present/absent) |
| `0x35400007` | `ENCRYPTION_CODE`: single-byte XOR mask (0 = none) | 1 byte |

So the file stores a **flag** (and optional hash records) — not real
encryption of the OLE2 container. The *table streams* can be XOR-masked with
the single byte `0xFF - code` when the flag is set (MPXJ's
`DocumentInputStreamFactory`/`EncryptedDocumentInputStream` do exactly that);
that is obfuscation, not cryptography. **[inference]** from MPXJ's source — no
password-protected .mpp is on disk.

Reader contract (tested by patching the byte in memory through `CfbDocument`):

* flag 0x00 (all 12 fixtures): reads; `password_required_to_*` false.
* flag 0x02 only: **reads normally** and reports
  `password_required_to_modify = true` + a warning "write-reservation
  password: the file is read-only, not encrypted".
* flag 0x01 or 0x03: throws `mpp::Error` naming `PASSWORD_FLAG` and key
  0x35400000 — the reader cannot authenticate a read password.
* any flag with a non-zero `ENCRYPTION_CODE`: throws `mpp::Error` naming
  `ENCRYPTION_CODE` — the streams would be XOR-masked and that is refused
  rather than decoded without evidence.

## 6. Proved vs inferred

**Measured / proved from the bytes (with the independent check named):**
task row size and every task offset; uid/ID order; duration/format table;
resource row + type bits; link word order; assignment row; stored
parent/level; milestone and the twenty flag bits; calendar column order;
subproject record and paths; version string and the absence of password
records in every fixture. Independent checks: MPXJ JUnit expectations for the
same fixture files (counts, Task #1 values, relation types/lag, UniqueID
offset 8388608, milestone) and internal cross-checks (assignment dates == task
dates, project row dates == task span, row sizes from FixedMeta offsets).

**Inference (stated as such):**
* the third slack word (+32) is MPXJ's FinishSlack and is exposed as
  `total_slack` (MPP12 has no separate total word; they coincide on an
  unconstrained task) — no COM oracle;
* the project row's dates are +88/+92 (same offsets as a task; for
  `mpp12header` the stored project start is 17:00, which looks odd but is what
  the bytes say);
* the XOR password mask (from MPXJ, no protected fixture);
* 16-byte blocks are "null tasks" (no name/VarMeta, MPXJ skips them);
* the Q4 "resource calendar" name resolution is left to core/cal (the reader
  reports the stored uid/name pairs only).

**Refused / unsupported (never guessed):**
MPP9/MPP8/MPD; MPP12 baseline, timephased, recurring-task *parameters*,
assignment contours and the `212/` view state are opaque (existing scope);
a read password and XOR-masked streams; subproject item layouts other than
type 0x01/0x08 (warned with the item offset, rest not parsed); a subproject
read-only flag (no byte located); a MPP12 task row whose size is neither 16
nor 264 (warned and skipped, and the whole table is refused when every data row
is unsupported — the MPXJ-written 206-byte `*-from14.mpp` variant);
a MPP12 hour/week calendar decode (core/cal).
