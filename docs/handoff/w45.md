## 1. What is done

### New API

`core/mppwrite/add_delete.h` / `.cpp`:

- `add_task_row(doc, NewTaskRow const&, path, table = "114/TBkndTask") -> AddedRow`
- `delete_task_row(doc, uid, path, DeleteOptions const& = {}, table) -> DeletedRow`

Both are all-or-nothing, write the file, re-open it from disk, re-read every
written fact, and only then replace `doc`. They never write `214/`.

Add appends: FixedData +202, FixedMeta +47 (entry `+0=0`, `+2=8`,
`+4`=offset), Fixed2Data +64 (record `row+3`, `+16` = `row+1`, new identity,
`+24` = project identity), Fixed2Meta +96 (`+4`=record offset, `+8`=`0x7f`/`0xff`),
VarMeta +96 (8 entries: Name, `0x0b4000a4/a5/a8/a9/aa`, `0x0b400563/564`), and
Var2Data with those 8 blocks appended; every header count/size word is updated.
The FixedMeta header `+4` flags word is left untouched on add (stays 4).

Delete tombstones: FixedMeta entry `+0=0x02`, `+2=0`, **and FixedMeta HEADER
`+4 |= 0x02`**; no stream shrinks; later live rows' `FixedData +0` decremented;
the uid's VarMeta entries removed (both uid families); its Var2Data blocks left
orphaned; Fixed2Data/Fixed2Meta/Var2Data required byte-identical.

**The header bit is the gate (measured).** Project's own files carry
`FixedMeta +4 = 0x00000004` with no tombstone and `0x00000006` once a row is
deleted (`w10-adddel-back/-del`, PROJECT_B). The first W45 delete fixtures omitted
it and Project reopened them with the deleted task still visible (3 tasks where 2
were expected); after `+4 |= 0x02` the coordinator's read-only open reports
**2 tasks** for both `w45-del-middle-a.mpp` (entries removed) and
`w45-del-middle-b.mpp` (entries kept). The shipped path is A: header bit + our
cleaner VarMeta removal. Project's retained-entry churn is not needed.

Refusals: uid 0, duplicate/unknown/already-tombstoned uid, empty name, broken size
identity (including PROJECT_A, whose FixedMeta declares 87 entries but holds 88), and by
default a delete that leaves a live link/assignment naming the uid
(`DeleteOptions::allow_dangling` opts in and warns).

### Reader fix (scoped cross-lane exception, granted by the brief)

`core/mpp/reader.cpp`: Task liveness is now

```
live = (VarMeta group present) AND (FixedMeta entry +0 == 0x00)
```

with `+0 = 0x02` the tombstone Project writes. If FixedMeta is absent/unreadable
the state is "unknown" and the VarMeta group alone decides, as before. A
tombstoned row that still has a VarMeta group is reported in
`Document::skipped_rows` with reason `"FixedMeta entry is a tombstone (+0 = 0x02):
deleted row"`; the other skip reason is unchanged. PROJECT_A 83 and PROJECT_B 73 tasks are
unchanged (663 reader checks). The liveness fix is independent of the header `+4`
bit, and the delete fixtures with `+4=6` still read as the expected live sets.

## 4. Verified vs inferred

Verified locally and independently (`olefile` 0.47 plus the C++ tests): the
stream/size/count deltas above, `214/` untouched, the tombstones, the ID
renumbering, `FixedMeta +4` (4 -> 6 on delete, untouched on add), byte-identical
re-emission, clean `check()`/`check_table()`, and the independent reader's live
counts/UIDs/IDs on every fixture.

Verified by the oracle (coordinator, read-only Project open, 2026-10-22):
add / add2 / add-values reopen as 4 / 5 / 4 tasks (priority 600 survived; the
auto row's percent re-reads as 0 and dates recalculate); `w45-del-middle-a` and
`w45-del-middle-b` reopen as 2 tasks with durations 2400 + 960. So the header
`+4` bit is required and sufficient, and neither Project's VarMeta retention nor
its re-keying is needed.

Still inferred: the clone semantics for a row added to a non-fresh file
(progress, milestone blob, whether the new row should be auto). The measured
input is Project's own `Tasks.Add` stream diff, its tombstone bytes, and the
oracle opens above.
