`clear` takes no field id by design: the measured empty form is a single

## 2. What is actually inverted (measured, not guessed)

The inverse is exact for the measured extent, and **byte-for-byte for the
wave-14 pair**:

```
payload := u32 inner_size (= payload size), u32 count,
           count * { u32 field_id, u32 relative_block_offset },
           blocks, first at relative 8 + 8*count, tiling to payload end
block   := u32 13, u32 0xffffffff, 7 * u32 block_span,
           UTF-16LE formula text, u16 NUL [, u32 trailer]
```

Evidence (2 = wave-14 pair, 6 = committed `tests/data/synthetic-props.bin`):

* All **8** measured blocks have all seven span words equal to the block's own
  byte span (68, 76, 116, 92, 76, 76, 76, 76). The 168-byte two-formula record
  regenerated by this code is **byte-identical** to Project's saved record; the
  test carries that 168-byte payload as a literal.
* Entries are written in **ascending field id** (0x0b400036 then 0x0b400058 in
  the wave-14 pair; all six wave-10 entries ascend).
* `[Duration]` is stored as **188744967** (`Task.DurationText`, 0x0b400507), not
  188743709 (`Task.Duration`, 0x0b40001d), even though `core::formula::parse`
  resolves the name to the latter. The writer maps that one id; measured in the
  wave-10 six and the wave-14 pair.
* Empty form: payload `08 00 00 00 00 00 00 00` (count 0), exactly 8 bytes.
* Header: the writer preserves the input's own size-word delta (`stream_size - 4`
  on 114/Props; Props14's delta is different and preserved), writes
  `delta = old_size - header.size_word` and `new_word = new_size - delta`, and
  writes the record's new payload length. Record count and `declared_entries`
  are not touched (Project leaves them unchanged).
* Every other record is copied verbatim and the opaque tail bytes are copied
  verbatim; the project-name record `0x02400008` and the tail are never
  synthesised.

### The second record that must change: `0x02401392`

The brief says "no other record changes except the project-name record and the
tail". That is **not** what the files show. `0x02401392` (kind 2, u16) is a
**"custom-field data in use" flag**, and the writer must maintain it:

| fixture | formula table | custom-field values | flag |
|---|---|---|---|
| `synthetic-base.mpp`, `w14-formula-control.mpp` | empty | none | **0** |
| `probe-v1.mpp`, `link1.mpp` | empty | none | **0** |
| `w10-fieldvalues.mpp`, `w10-flag-on.mpp`, `w14-cost.mpp`, `w14-assignfield.mpp` | empty | yes | **1** |
| `w10-formulas{,2,3}.mpp` | 6 formulas | (formulas only) | **1** |
| `w14-formula.mpp` | 2 formulas | (formulas only) | **1** |

So it is not a formula count: it is 1 with an empty formula table when only
custom-field *values* are set. Behaviour implemented:

* `set_custom_field_formula` writes **1**.
* `clear_custom_field_formula` writes **0 only when it actually removes
  formulas**; a no-op clear on an empty table leaves the flag byte-for-byte
  alone (needed for the value-only case above and for no-op identity).
* `replace_formula_record` never touches the flag (pure no-op re-encode).
* The record must be present with kind 2 / length 2; otherwise the writer
  refuses rather than guess.

Risk recorded for the coordinator: if the app clears all formulas from a
project that still holds custom-field **values**, the flag should stay 1, but
`core/props` cannot see the other streams that prove those values exist. The
app must restore it, or `clear` should only be used when the project has no
custom-field values.

### The wave-14 control/edited pair, re-measured

`corpus/probe/w14-formula-control.mpp` -> `w14-formula.mpp`
(`114/Props`: 88,720 -> 88,864 bytes). The brief says "grows by exactly 160
bytes", but 88,864 - 88,720 = **144**: the formula record grows 8 -> 168 (+160)
while the project-name record `0x02400008` shrinks 42 -> 26 (-16) because the
two saves carry different project names. Other changed records are per-save
identity churn of the same size (`0x02400029`, `0x024013c2`) plus the flag
`0x02401392` 0 -> 1. The tail differs in **one byte only**: the typed property
at tail+16 key `0x02000001` reads 0 in the control and 16 in the edit
(tail+28). No tail offset/pointer needed fixing, which is why copying the tail
verbatim at its shifted position is valid for a +160 growth. Measured with
olefile 0.47 and a struct pass, not inferred.

## 3. Refusals (all tested)

1. Field id 0, unknown field id, or a known but non-custom Task field.
2. Formula that `core::formula::parse` rejects (unknown field reference,
   unbalanced call, ...). The same parser/depth guard (`kMaxFormulaDepth = 64`)
   the app uses.
3. Layout the writer does not understand: no formula record, more than one,
   kind != 0, `inner_size != payload size`, count 0 on a payload other than 8
   bytes, block offsets that do not tile the payload, a block without the
   `13 0xffffffff` header, a block without an in-span UTF-16 NUL, empty text,
   duplicate field ids; and for the flag record: missing, duplicate, wrong
   kind, wrong length.
4. A stream that does not parse at all, and a rebuilt stream that does not
   re-parse with the same record count, the same tail length, byte-identical
   tail bytes and every non-formula, non-flag record byte-identical.

One decoder limitation is surfaced as a refusal rather than papered over:
`extract_formulas` only scans a formula record that contains the `MSPJ` token.
A **lone constant formula** (`"42"`) on an otherwise empty table therefore
cannot be read back, so `set` refuses it. A constant formula added next to a
formula that does have a field reference is readable and is accepted (the gate
is per record and the table parser handles every entry). No formula with a
non-BMP character survives the writer's read-back check either, because
`extract_formulas` decodes UTF-16 code units 1:1; that is also refused.

## 7. Proved vs inferred, and what is copied rather than generated

**Proved here** (bytes, offsets, or a passing test with a re-runnable command):

* The empty form, the table framing, the seven span words = block span on all
  8 measured blocks, ascending field-id order, the 168-byte two-formula record
  reproduced byte-for-byte, header delta preservation, tail byte preservation,
  the flag's 0/1 correlation across twelve fixtures and its maintenance rules,
  every refusal above.
* Project's `[Duration]` -> 188744967 rewrite (two independent fixtures).
* No-op re-encode is byte-identical on the empty base and on the 568-byte
  six-formula record.
* Set-then-clear restores the raw `114/Props` stream of `synthetic-base.mpp`
  byte-for-byte.

**Copied, not generated** (the coordinator should know):

* **Existing blocks are copied verbatim**, including the optional 4-byte
  trailer. The trailer is present on 3 of the 6 wave-10 blocks and absent on
  both wave-14 blocks; its meaning is **not** inverted. In the measured cases
  the four trailer bytes decode as a NUL-terminated 1-char UTF-16 string
  (`"g"`, `"r"`, `"0"`), but nothing proves what it means. `set` of a
  *different* field preserves trailers, but a **newly generated block has no
  trailer** (what both measured Project-written wave-14 blocks do).
* The seven span words are generated as one value repeated; that is the whole
  measured invariant, but why there are seven and why they repeat is not
  explained.
* The 2-byte flag value is generated from the operation (set 1, real clear 0),
  not copied; its *meaning beyond the correlation* is inferred.

**Inferred / open:**

* That Project will *open* a file written this way. No oracle run was possible
  from this stream (COM is coordinator-only). Validation is our own parser
  (`core::formula::parse`), the decoder (`extract_formulas`) and a structural
  re-parse of the container.
* The exact meaning of the `0x02401392` flag (values vs formulas) beyond the
  measured correlation, and therefore the safe value when formulas are cleared
  from a value-bearing project.
* Ascending order is measured on 8 entries; treating it as Project's rule is a
  deliberate canonicalisation, not proved.
* The full expression-blob grammar (what each of the seven words means, when a
  trailer appears, whether a trailer is required for some operators) is open.
* The `[Duration]`-to-DurationText mapping is the only such quirk measured; other
  `*Text` variants were not exercised.
* `0x0240008` project name and the 85,408-byte opaque tail are never
  synthesised; the only measured edit to the tail between the wave-14 pair is
  the save-property word at tail+28 (key `0x02000001`, 0 -> 16), which the
  writer does not touch.
