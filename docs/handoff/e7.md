## 1. The byte search and the evidence chain

### Where the flag is not

* **`ProjectRow` itself (the 202-byte row 0).**  The row supplies ID, UniqueID,
  duration, priority, percent, the calculated Start/Finish and the Name block;
  no byte of the fixed row differs in a way that tracks this setting.  The
  fixed row is also shared with MPP12, where the option did not exist.
* **The task records / `FixedMeta`.**  The per-row `0x80` manual bit is a
  *task* flag (already exposed as `Task::manually_scheduled`), not the project
  default: all three fixture tasks are manual while the file's default is a
  separate word, and PROJECT_A's 83 tasks are non-manual while its default is
  Auto.
* **`214/Props`** (view state): no candidate matched the labelled files; the
  setting is a document property, not a view property.

### Where it is

`114/Props` (MPP14), or `112/Props` in a 2010+ project down-saved to MPP12,
record **`0x024013c8`**, kind 2, a u16: **0 = Auto Scheduled, 1 = Manually
Scheduled**.

### How the record id was identified (not guessed)

1. The decompiled Project binary has a project-property **name table** in
   `decompiled/part_0000.c` `FUN_1401b8a70` (121 names, `DEFAULTCALENDAR`,
   `QDISPLAYESTIMATED`, `QISNEWTASKSESTIMATED`, … `QNEWTASKSAREMANUAL`, …).
   `QNEWTASKSAREMANUAL` is element **64** (stack slot `local_1e8`, i.e.
   `local_3e8 - 64*8`).
2. The same binary's props dump helper **`FUN_14034ea20`**
   (`decompiled/part_0003.c:11423`) maps a project record id to that table with
   `index = (id & 0xffff) - 5000`; with `0x1388 = 5000` the id of element `i`
   is `0x02401388 + i`.  Element 64 → **`0x024013c8`**.  (An earlier handoff
   named `FUN_14034ede6`; that is a label inside `FUN_14034ea20`, not a
   function — audit A-6.)
   **The decompiled `.c` files are local-only and git-ignored.**  The committed
   evidence is the derived `analysis/project_property_names.tsv`, generated by
   `scripts/gen_project_property_names.py`, and the reader test
   `test_project_property_names` checks the id arithmetic against it.
3. The index rule is independently checked on **other names from the same
   table** against the same files: `QISNEWTASKSESTIMATED` (`0x0240138a`) matches
   its MSPDI `<NewTasksEstimated>` value (0 for PROJECT_A/B, 1 for the three
   probe exports); `DAYSPERMONTH` (`0x0240138f`) is 20; `PROJECTCURRENCYCODE`
   (`0x024013bb`) is `"AUD"`; `CREATIONSYSTEMTIME` (`0x02401394`) is a 16-byte
   SYSTEMTIME; `BASELINE1..10SAVEDATE` (`0x02401395..0x0240139f`) are
   `0xffffffff`/dates.  The mapping is therefore not a single lucky guess.
4. A second code path ties the two ids together: when the dispatcher sets
   `0x024013cb` (`QCANPINTASKS`) to 0 it calls the getter for `0x024013c8`
   (`decompiled/part_0000.c` line ~81234) — the "pinning disabled ⇒ new tasks
   manual" rule of a project that cannot pin tasks.

### Candidates rejected

The project props differ between the Auto and Manual sample in many places, so
a 0/1 coincidence was not enough.  Rejected, with the reason:

* `0x0240138a` — maps to `QISNEWTASKSESTIMATED`; its values follow MSPDI
  `<NewTasksEstimated>`, a *different* option that happens to share the 0/1
  pattern here.
* `0x0240138d` (`TREATSUBASSUMMARY`), `0x02401392` (`DOCHASALIAS`) and
  `0x024013c5` (`COMBOPROPINFO`) map to *other* named properties in the same
  table, so they are not this option.  Only `0x024013c8` maps to
  `QNEWTASKSAREMANUAL`.
* `0x02400018`, `0x02400031`, `0x0240003c`, `0x02400043`, `0x0240004b`,
  `0x02400050` — low-word ids, i.e. NOT in the project-property name table at
  all (that table covers ids 0x1388+); they are other project/prefs records.
* `0x02400035/47/4d/55/5b/5e/26/27/28` are not booleans (0x02/0x03, 1252/850,
  a status date, a locale id…), not this checkbox.

## 2. The reader field

```cpp
bool ProjectRow::new_tasks_manual = false;         // meaningful only when stored
bool ProjectRow::new_tasks_manual_stored = false;  // the file carries the record
```

`parse_document()` calls `decode_new_tasks_manual()` after the table parse, for
MPP12 **and** MPP14, using `format.table_root` (so `112/Props` works too).  The
framing is core/props': 16-byte header, then `u32 length, u32 id, u32 kind,
payload`, stopping at the first id whose byte 2 is not `0x40`; core/mpp does not
link core/props for this one record.  A malformed record (wrong kind/length) is
reported in `Document::warnings` and leaves `stored = false`; a missing record is
silent (normal for 2007 files).

`mpp::read_new_task_mode(path)` reopens only the container + project props and
returns `{known, manual}`.  It exists because the Qt shell sees
`app::PlanInput` (which does not carry this field) and `PlanDocument` is owned by
S6; E7 must not edit `plan_document.*`.  It reads no task table, so the extra
open is cheap, and it never throws on an unreadable container (returns
`known = false`).

## 6. Verified vs inferred

**Verified by running** (quoted above): the record's value on 133 files;
`ProjectRow` on the fixture, PROJECT_A/B, the three labelled probes, a 2007
MPP12 file and a down-saved MPP12 file; `read_new_task_mode` agreeing with the
document; the status label on a real MainWindow for Manual, for the flipped
Auto copy and for PROJECT_A; 50/50 root, 1016 reader checks, 332/332 M2,
app_qt 15/15, fixtures OK.

**Direct evidence**:

* the record id ↔ `QNEWTASKSAREMANUAL` mapping from Project's own binary
  (name table + index rule, cross-checked on five neighbouring properties);
* the value labels from Project's own MSPDI exports (5 files, 10/10 values)
  and, for PROJECT_A, the clean capture's status bar.

**Inference (reasonable, stated, not measured here)**:

* that Project's status bar reads "Auto Scheduled" exactly when the record is 0
  — supported by the capture on PROJECT_A and by the option's meaning, but not
  measured on a file whose flag we flipped inside Project (no COM in this
  wave);
* that a *new* file created by a Project configured Auto would store 0 (we
  only see Auto files written by an Auto-configured Project; no fixture toggles
  the option);
* the fallback choice for an undecodable value is the Manual text (operator
  decision 11 / the brief), not a claim about the file.

**What remains unknown / not done**:

* the operator's real file in its current location is not on this machine
  (network access denied); the local `corpus/project_a.mpp` is the same stored
  table as the clean capture and is Auto, which is why the status now matches
  the reference on it.  A capture of *this* file's status was not taken this
  wave (the clean capture is the visual evidence).
* no writer: the setting is decoded, not saved.  A new/edited project still
  writes whatever the rest of the writer copies; `core/mppwrite` has no API for
  this record.  E7's ownership was `core/mpp/**`; adding a writer would need a
  measured Project acceptance run.
* the exact timestamp/meaning of `DOCHASALIAS` and `TREATSUBASSUMMARY` (the two
  rejected 0/1 neighbours) was not chased; they are simply not this option.
