## 1. CFB slack in `mppwrite::CfbDocument` (M6's open item 6)

### What was wrong

`core/mppwrite/cfb_writer.cpp` `CfbDocument::parse()` rejected any file whose
FAT was shorter than its sector count:

    '…/sf248.mpp': FAT covers 768 sectors but the file has 959

`core/mpp` has treated the same file as slack since wave 20 M6 (it loads all 81
streams and records `"191 unreferenced sectors"`), but `engine_diff_tests
--dump` opens `mppwrite::CfbDocument` for the stream inventory *after* the
reader accepts the file, so the dump exited 1 on a file the reader had already
loaded.

### What changed

* `core/mppwrite/cfb_writer.h`
  * new `std::vector<std::string> const& warnings()` (the recoverable container
    anomalies, in the order found) plus the `warnings_` member;
  * a **FAT SLACK** paragraph in the file comment: such a document is
    *readable* but not *byte-identically re-emittable*, because `to_bytes()`
    derives the FAT from the chains the model knows (the header's
    sector-placement claim); `to_bytes()` refuses one and `check()` reports
    "not round-trippable".  Every file the round-trip tests feed covers all
    its sectors, so their byte output is unchanged.
* `core/mppwrite/cfb_writer.cpp`
  * `parse()` now pushes the same message shape as `core/mpp/cfb.cpp` instead of
    throwing:
    `"<N> unreferenced sectors: the FAT describes <F> of the file's <S> sectors;
    the remainder is not part of any chain"`;
  * `warnings_.clear()` at the top of `parse()`;
  * the top-of-file layout claim now says **re-emitted** files have no orphans,
    and names the slack case.
  * Nothing else in the parser changed: `chain_from()` still throws
    `"<what>: sector N is past the end of the allocation table"` when a chain
    walks past the FAT, so truncation stays fatal.

### Measured result

```text
build\e6-w21\Release\engine_diff_tests.exe --dump corpus\imported\sf248.mpp build\e6-w21\dump\sf248.json
engine_diff: container warning: 191 unreferenced sectors: the FAT describes 768 of the file's 959 sectors; the remainder is not part of any chain
exit=0
```

The JSON is a normal `engine-diff/2` dump: 0 live tasks, 7 assignments, 81
streams (the same 81 the reader sees; M6's note), `file.streams` present.  The
three numbers are the measured ones, not derived from the brief.

### Regression test (`tests/roundtrip_cfb.cpp`, target `mppwrite_roundtrip_cfb`)

Synthetic and corpus-free, so it also runs on a machine without `corpus/`:

* `minimal_cfb()` builds a **valid** 3-sector CFB v3 from bytes — directory
  sector 0 (root + one 512-byte stream + two free slots), FAT sector 1, payload
  sector 2;
* a compact CFB parses with **no** warning (no false positive), the stream reads
  back, and `to_bytes()` is **byte-identical** to the input (the writer's byte
  output for a valid file);
* appending 140 unreferenced sectors (3 + 140 = 143 sectors, one 128-entry FAT)
  loads with exactly one warning naming `15 unreferenced sectors`, `FAT
  describes 128`, `file's 143`, and the stream still reads;
* `check()` reports the file as `not round-trippable` and `to_bytes()`
  refuses with the warning text instead of silently emitting a *different*
  file (the writer derives the FAT from the chains it knows);
* the fatal half: the stream's start is patched to sector 130 — physically
  present (143 sectors) but with no FAT entry — and the load throws a
  `mppwrite::Error` whose text names `130` and `allocation table`.

`mppwrite_roundtrip_cfb`: **1682 -> 1693 checks, 0 failures** (11 new
checks).
A valid-file dump (`tests/data/synthetic-base.mpp`) is byte-identical between
the wave-20 and wave-21 binaries and emits no warning.

### Dump reporting (`tests/engine_diff_tests.cpp`, the `--dump` path only)

`dump_file()` prints every `container.warnings()` line to **stderr** as
`engine_diff: container warning: …` after both loads succeed.  The JSON gains no
leaf, so the harness comparison is unchanged (all 8 oracles still pass and the
`--selftest` tamper check is untouched).

## 2. `constraint-mso`: the decision

**Decision: measure and pin the rule, but do not let it buy a pass.**  The rule
is implemented as a pure function and a self-test model, and the nine-row table
in `docs/engine-parity.md` "Wave 20" is its regression.  It is **not** applied
to the file a scored scenario compares, and not in production, so
`constraint-mso` stays FAIL 1/247 and the suite stays 7/8.  No oracle, scenario
or `tests/data` file was edited.

### Why not the "stop comparing" option

`tests/data/scenarios/constraint-mso.oracle.json` stores `tasks[3].duration_ticks = 12000`
while Project's own COM surface reports `Task.Duration = 960 minutes` (9600
ticks) throughout, so the oracle field is a *stored file word* that Project's
object model contradicts.  Excluding it in the harness would be defensible, but
it would (a) remove a real field from every scenario's comparison and (b) need
`scripts/engine_diff.py`, which is outside this stream's ownership.  The
measured rule reproduces all nine rows, so the honest option was to model it,
pin it, and keep it out of the score until the product writes it.

### The measured rule (as implemented)

For a **manual, pinned** row whose stored constraint is **Must Start On** and
whose kept start day is **not a working day** for its calendar, Project's stored
`+84` duration word on save is:

    stored duration = plan duration
                    + working ticks in the start day at/after the start clock,
                      using the calendar's STANDARD DAY WINDOWS

The kept dates (`+104/+108`), the calculated pair (`+96/+100`), the late pair
(`+112/+116`), the slack words and the assignment work are the *plan's*: only
the duration word moves, which is the internally inconsistent state Project
itself saves (COM still says 960 min).

Evidence rows (all `synthetic-base`, off-calendar starts; `docs/engine-parity.md`
"Wave 20"):

| keep start | plan duration | increment | stored |
|---|---|---|---|
| Sun 13:00 | 9600 (2 d) | 2400 (4 h, 13:00-17:00) | **12000** |
| Sun 13:00 | 4800 (1 d) | 2400 | 7200 |
| Sun 08:00 | 4800 | 4800 (8 h) | 9600 |
| Sun 10:00 | 4800 | 3600 (6 h) | 8400 |
| Sun 15:00 | 4800 | 1200 (2 h) | 6000 |
| Sat 09:00 | 4800 | 4200 (7 h) | 9000 |
| Fri 13:00 (working) | 4800 | 0 | 4800 |
| task 2, Sun 13:00 | 14400 (3 d) | 2400 | 16800 |
| task 1, Sun 13:00 | 24000 (5 d) | 2400 | 26400 |
| no constraint (control) | 9600 | 0 | 9600 |

### Trigger scope: MSO, and only MSO (measured)

The committed `constraint-snet` oracle is the negative control: uid 2 is
**manual**, starts on the same off-calendar Sunday 13:00, and carries an SNET
constraint (type 4) with a date — yet its stored duration is **14400**, no
increment.  So "a constraint is applied" is not the trigger; the measurements
and the oracle together select **Must Start On (PjConstraint 2)**.  The
implementation checks `stored.constraint_type == 2` and a stored date, and the
self-test asserts the SNET row stays 14400.  Other constraint types are
unmeasured and deliberately untouched.

### Where it lives / save-only

* `tests/engine_diff_tests.cpp`:
  * `off_calendar_start_bump(calendar, start)` — the pure rule (0 on a working
    day; otherwise the remainder of the standard day windows after the start
    clock);
  * `calendar_for(input, uid)` — the row's task calendar, else the project
    calendar;
  * `Applier::model_project_save(bool)` -- an explicit opt-in used **only by
    the self-test's five end-to-end cases**.  The scored scenarios leave it off,
    so their compared file is exactly what the production save path writes.
    Measured with the opt-in: `.work.mpp` = 9600, final `.mpp` = 12000, with the
    same kept dates and late pair; bumping the intermediate pass would feed
    12000 back into the plan and write 14400 on the next pass.
* `core/plan/**` and `mppwrite::save_plan` are **not** changed: the production
  save path writes the plan duration (9600 for this edit).

### Regression in the self-test

`check_mso_duration_table()`:
* asserts the **nine-row table's increments and stored totals** against the
  pure rule using a `core::cal` build of `synthetic-base`'s calendar (the four
  starts a fixture row cannot be moved to — Sun 08:00/10:00/15:00, Sat 09:00 —
  are rule-level: the manual Start write path is unsupported, `row_writer.h`);
* runs **five end-to-end applier cases with the opt-in on** and reads `+84`
  back from the saved file with `core/mpp`: task 3 2 d -> 12000, task 3 1 d ->
  7200, task 2 3 d -> 16800, task 1 5 d -> 26400, no-constraint control ->
  9600 (the scored scenarios do not opt in);
* the built-in `constraint-snet` case also asserts uid 2 stays 14400.

`engine_diff_tests` self-test: **236 -> 265 checks, 0 failures** (+29).  The
`--apply` path logs every bump on stderr (`engine_diff: save: uid N duration
word gains T ticks: …`), so the rule is visible in a run.

## 4. Verified vs inferred

**Verified by measurement (build, tests, bytes)**

* sf248: `--dump` exits 0, prints the 191/768/959 warning; the JSON has 81
  streams, 0 tasks, 7 assignments.
* A valid CFB still round-trips byte-identically (1693-check corpus sweep +
  the synthetic compact-CFB identity check), and a valid-file dump is
  byte-identical between the wave-20 and wave-21 binaries.
* A chain past the FAT throws a positioned `mppwrite::Error` naming the sector
  and the allocation table; a slack document's `check()` reports `not
  round-trippable` and `to_bytes()` refuses instead of emitting a different
  file.
* Under the self-test opt-in the MSO row's `+84` becomes 12000 with kept
  `01-04 13:00 -> 01-06 12:00` and late `01-07 13:00 -> 01-09 12:00`; the
  intermediate `.work.mpp` is 9600.  The scored suite still reads 9600 vs
  Project's 12000 -- the product boundary.
* M2 332/332, ctest 50/50, no oracle/scenario/fixture change.

**Inferred / boundaries (stated, not hidden)**

* The **standard day windows for a non-working start day** are taken from the
  first non-empty pattern in the calendar's default week (next working
  weekday's shape).  Every measured row is on `synthetic-base`, whose five
  working weekdays are identical (08:00-12:00 + 13:00-17:00), so the template is
  not measured across a calendar with different weekday shapes, and the
  *cause* of Project's increment is still not understood — only its measured
  value.
* The **trigger is MSO-only** because that is what the nine measurements and
  the SNET oracle show.  MSO combined with actuals, an elapsed duration, no
  task calendar, or a different constraint type is unmeasured and untouched.
* The rule assumes the input row's `+84` is the **unbumped** plan duration (true
  of the committed fixture before the constraint is applied).  Re-saving an
  already-bumped Project file is not modelled: the applier already plans from
  the stored duration word, and that limitation predates this change.
* The rule is applied only by the **self-test's opt-in**.  Neither the scored
  scenario applier nor production (`mppwrite::save_plan`/`core/plan`) applies
  it, so the differential suite and a Qt/`app` save of the same edit write
  9600.

**Not verified**

* No COM session and no real Project-written MSO file beyond the nine recorded
  measurements were available (COM is the coordinator's surface); the
  `constraint-mso` oracle is the measurement used.
* The four start variants (Sun 08:00/10:00/15:00, Sat 09:00) are asserted at the
  rule level, not end-to-end through a saved file, because the writer cannot
  move a manual row's Start (`row_writer.h`).
* The local Qt build was not needed and not run.

  `--dump sf248.mpp` -> exit 0 with the 191/768/959 warning.

So the wave-21 engine score is **7/8**, not 8/8.  The rule is understood and
