### Extracting a `214/` tree for the CLI

The module deliberately does not open CFB files (no `core/mpp` dependency). The
CLI takes an extracted tree, one file per stream part:

```python
import glob, os, olefile
for path in glob.glob('corpus/probe/*.mpp'):
    root = os.path.join('build', 'dump-' + os.path.splitext(os.path.basename(path))[0])
    o = olefile.OleFileIO(path)
    for entry in o.listdir():
        full = '/'.join(entry)
        clean = full.strip()
        if not clean.startswith('214/'):
            continue
        target = os.path.join(root, *clean.split('/'))
        os.makedirs(os.path.dirname(target), exist_ok=True)
        open(target, 'wb').write(o.openstream(full).read())
    o.close()
```

Then `viewstate_report --dump build\dump-w10-prefs-base`. The CFB directory names
really carry three leading spaces (`'   214/CTable/Var2Data'`); `core/mpp/cfb.cpp`
trims spaces for its own lookups, and the extractor above strips them.

## 4. Measured framing (all 33 streams x 3 fixtures)

Same four-part shape as the `114/` tables.

- **FixedData**: rows of a class-specific size; row starts `u32 ordinal`
  (1-based, equals the VarMeta uid), NUL-terminated UTF-16 caption at +4, and a
  16-byte identity/GUID-like value in the last 16 bytes (churns on every save).
  The 230-byte classes also carry a UTF-16 display caption at +136 (`&Entry` ->
  `Entry`).
- **FixedMeta**: 16-byte header `magic 0xfadfadba`, `flags` (4), `declared_count`,
  `fixed_data_size`; entries of `entry_size = (size-16)/declared_count`:
  `+0 u16 state` (0), `+2 u16 var_count` (equals the VarMeta entry count for the
  uid), `+4 u32 fixed row offset`, rest opaque. `CEdl` is the only 11-byte entry
  measured; the other classes are 10.
- **VarMeta**: 24-byte header `magic, 0, declared_count, 0, 0, var2_size`
  (`var2_size` == Var2Data stream size); entries `{uid, offset, key}`. Offsets
  point at a block's length word and are not stored in block order (`CV_iew`
  groups entries by uid while blocks are sequential).
- **Var2Data**: back-to-back `u32 payload_length` + payload. Every block is named
  by exactly one VarMeta entry in the measured files; the parser still reports
  unreferenced blocks instead of hiding them.
- Row sizes: CTable 230, CFilter 230, CGrouping 230 (2 rows), CV_iew 138
  (3 rows), CEdl 160 (1 row). Derived from the first two FixedMeta offsets
  (single-entry streams: the whole FixedData), then every offset is validated.

## 5. CTable -- the persisted table definition (the product result)

Each table is one 230-byte fixed row plus one VarMeta block keyed
`0x20400006`. The block payload starts with a 12-byte header:

| off | field | measured |
|---|---|---|
| +0 | `u32` table ordinal | equals FixedData +0 and the uid |
| +4 | `u16` last column index | `column_count - 1` |
| +6 | `u8` format word | 1 in every measured table |
| +7 | `u8` date-format override | `0xff` default; **`0x05`** after `DateFormat=5` |
| +8 | `u32` table flags | 6 stock, 2 after the wave-10 TableEdit save; semantics open |
| +12 | columns | 115-byte records |

Column record: `+0 u32 field id` (task `0x0b40xxxx`, resource `0xc40xxxx`),
`+4` nine opaque bytes, `+13` UTF-16 NUL-terminated title (max 51 code units).
The stock Entry table has 9 columns:

`0x0b400017, 0x0b4000cd, 0x0b400500, 0x0b40000e, 0x0b400507, 0x0b400505,
0x0b400506, 0x0b40002f, 0x0b400031`

Only the Name column (`0x0b40000e`) stores a title (`Task Name`). The report:

```
table 1 "&Entry" display="Entry" columns=9 date_format=0x000000ff flags=6 block=0+1047
  col 0 field=0x0b400017 title="" header=061008010801000000
  ...
  col 3 field=0x0b40000e title="Task Name" header=181008000803000000
  ...
```

The `column_count - 1` rule is proved beyond the single-table fixture: a probe
file with an 8-table CTable collection (4, 7, 9, 10 and 14 columns) has
`+4 = n-1` in all eight. Re-run the scan (it prints the corpus-derived file
name itself, so the name is not written here):

```python
import glob, os, struct, olefile
for path in sorted(glob.glob('corpus/probe/*.mpp')):
    o = olefile.OleFileIO(path)
    if not o.exists('   214/CTable/VarMeta'):
        o.close(); continue
    vm = o.openstream('   214/CTable/VarMeta').read()
    v2 = o.openstream('   214/CTable/Var2Data').read()
    if len(v2) <= 2000:
        o.close(); continue
    count = struct.unpack_from('<I', vm, 8)[0]
    rows = []
    for i in range(count):
        off = struct.unpack_from('<III', vm, 24 + i * 12)[1]
        length = struct.unpack_from('<I', v2, off)[0]
        last = struct.unpack_from('<I', v2, off + 8)[0] & 0xffff
        rows.append((last, (length - 12) // 115, v2[off + 7]))
    print(os.path.basename(path), count, rows)
    o.close()
```

Expected shape: `(last_index, columns_from_size, date_format)` pairs with
`last_index == columns_from_size - 1`; every date format in that file is `0xff`.

## 7. CEdl -- last view/table names plus a file path (save churn)

`214/CEdl` is one 160-byte fixed row and one Var2Data block whose payload is a
complete Props document. The module parses it with `core/props`
(`props::parse_props`), which is the only Props-shaped block in the 214 tree
(CV_iew's main blocks have the same prefix but do not walk as Props records).

```
CEdl base:  records=14 tail=0   (466 B Var2Data)
CEdl col:   records=15 tail=0   (676 B; +210 B = one 198-byte path record)
CEdl date:  records=15 tail=0   (678 B; the same path, 2 B longer name)
```

The extra record's payload is a UTF-16 path. This is the entire W46-era
"214/Props +192" / CEdl growth explanation: a recent-file/last-view cache, not
table state. Do not commit an extracted CEdl blob.

`214/Props` is an ordinary Props stream (13,102 B, 47 records, 3,200 B tail,
declared 109); the CLI reports it via `core/props`. Its own diff is identity
churn plus a 2-byte CEdl-size word at stream offset 11402 (`466` -> `676` on the
column-add save; 676/678 for col/date).

## 8. Differential decode: the three prefs fixtures

All 96 streams hashed for each pair. Under `214/`:

| comparison | changes |
|---|---|
| base -> col ("add column") | `CTable/Var2Data` stream byte 12 = payload +8: `06` -> `02`; `CTable/FixedMeta` last byte `df` -> `d7`; `CV_iew/Var2Data` 96 one-byte colour changes in view 3; `CEdl/Var2Data` +210 B path record; `CEdl/VarMeta` size word; `CEdl`/`CTable`/`CV_iew`/`CFilter`/`CGrouping` FixedData identity tails; `214/Props` identity + CEdl-size word |
| col -> date (`DateFormat=5`) | **only** `CTable/Var2Data` stream byte 11 = payload +7: `ff` -> `05`; plus identity/path churn (CEdl path +2 B, its VarMeta/214-Props size words, all FixedData identity tails) |

### 8.1 The added Entry column is NOT in 214

The CTable block keeps **9 column records in all three fixtures**; the column
record bytes are byte-identical between base and col (the only table-block
difference is the flags byte). Byte scans over every stream of all three files:

- `57 00 40 0b` (Number1 field id): 2 hits per file, all in `114/Props`; **0
  hits under `214/`**.
- UTF-16 `Number1` (the Title/NewFieldName the oracle passed): **0 hits in any
  stream**.
- ASCII `Number1`: **0 hits**.

So the wave-10 "add a Number1 column to Entry" call did not persist a column.
The typelib (`analysis/typelib.tsv` line 9354) gives the real argument order:

```
TableEdit(Name, TaskTable, Create, OverwriteExisting, NewName, FieldName,
          NewFieldName, Title, Width, Align, ShowInMenu, LockFirstColumn,
          DateFormat, RowHeight, ColumnPosition, AlignTitle,
          HeaderAutoRowHeightAdjustment, HeaderTextWrap)
```

The oracle's first call was
`("Entry", True, False, False, None, "Number1", "Number1", "Number1", 10, 0, False, True)`
= `Create=False`, `OverwriteExisting=False`, no DateFormat, so it returned True
without adding a column. The second call set `OverwriteExisting=True` and
`DateFormat=5`, which is why the date-format byte is the only semantic 214
change. The two bytes that did change on the first save (`CTable` block `+8`
and the FixedMeta entry trailing word) are table-option/flag changes, not a
column: the nine column records and the count are unchanged.

### 8.2 Where DateFormat=5 lands (measured)

The date-format code is **`214/CTable` table-block payload byte +7**:

- `w10-prefs-col.mpp`: `0xff` (and `0xff` in all 86 other probe files checked)
- `w10-prefs-date.mpp`: `0x05`

col -> date differs in exactly one byte in the whole 214 tree, and that byte is
this one. `0xff` = "no override / use the application default" is an inference;
the 0x05 write is measured against the oracle's `DateFormat=5`.

### 8.3 The W50 `114/Props` tail word is not the format code

W50 measured tail key `0x00010001` value 298 -> 332 for base -> date. That is
exactly the size of `114/TBkndTask/Var2Data` (298 -> 332). That Var2Data change is
Project's own save compaction/churn: a stale 32-byte project-name block appears
at offset 76 and the real name block is relocated to the end (net +34 B), so the
Props word is size/offset-like, not the date format. The date-format correlate is the
CTable byte above. This is a correction to the W50 sentence "the real code may
be in 214/CTable": it is, at payload +7.

### 8.4 Other 214 changes are churn

The 16-byte identity at the end of every FixedData row changes on every save
(3-4 bytes per row). The CV_iew colour strings change only on the first save.
The CEdl path record is churn. None of these should be treated as table/edit
semantics.

## 9. API summary

```
msproject::viewstate::ViewState
  klass, fixed_meta, var_meta, var2, row_size, rows, blocks, block_refs,
  tables, views, embedded_props, warnings
  block_bytes(block), find_block_ref(uid, key)

parse_fixed_meta(span, FixedMetaStream&, ParseError*)
parse_var_meta(span, VarMetaStream&, ParseError*)
parse_var2(span, Var2Stream&, ParseError*)
parse_view_state(klass, PartSet{4 spans}, ViewState&, ParseError*)
describe_view_state(state, max_columns, max_blocks)
is_known_class(klass), block_kind(klass, key)
utf16_ascii(span, offset, max_units), preview_bytes(span, limit)
```

`TableDef` carries `caption`, `display_caption`, `identity`, block offset/length,
`header_ordinal`, `last_column_index`, `format_word`, `date_format`, `flags`,
`decoded`, and `columns` (`field_id`, 9 opaque header bytes, title, record
offset). Undecodable tables stay listed with `decoded == false` and a warning.

`ViewDef` carries ordinal/name/identity and its `ViewBlockRef`s (uid, key,
offset, payload_length, kind label, preview). `EmbeddedProps` carries the CEdl
Props document. Warnings are strings; nothing throws on malformed data.

`viewstate_report [--dump] [--inventory] [--class NAME] <root>` prints the
inventory (path, size, FNV-1a 64) and the decoded classes; `--dump` prints all
columns/blocks (otherwise 6 per table/view are shown), `--inventory` prints the
inventory only, and `--class` limits the decode to one class.

## 10. Measured vs inferred

Measured: inventory and the leading-space stream names; the four-part framing,
magic, header words, entry sizes, row sizes, ordinals, captions, identity churn;
the CTable block header and `column_count - 1` rule; the 9 Entry field ids, the
title offset/capacity; the date-format byte 0xff -> 0x05 in a single-variable
pair; the CV_iew 138-byte rows and 7-block key families; CEdl as a 14/15-record
Props document; every diff byte listed in section 8; absence of Number1 under
214; the typelib argument order.

Inferred: `0xff` = application default; the meaning of CTable block `+8` and the
FixedMeta entry trailing word (table options); the nine opaque column bytes; the
CV_iew key meanings beyond these fixtures; that the CV_iew colour change is
style churn; that `CEdl` is a recent-view/file cache rather than a table store.

## 12. Traps

- `TableEdit` returning True proves nothing; the typelib order is not the order
  in the oracle prose (Create and OverwriteExisting were both False).
- Do not look for a column count in stream sizes: the column-add save changed no
  214 size except the CEdl path.
- `CV_iew` main blocks have a Props-like header but are not Props documents;
  `props::parse_props` will accept one record plus a huge tail, so class identity
  decides, not content sniffing.
- The 16-byte FixedData identity is save churn; never diff it as semantics.
- `214/CEdl` contains a host path; do not commit an extracted blob.
- CFB names have three leading spaces (`'   214/...'`); the CLI/extractors must
  strip or keep them consistently.
- Do not write or patch `214/`; Project rewrites most of it itself, and the
  fixture pair shows cache churn independent of the edit.
- The committed blobs are only Var2Data; the test builds the other three parts
  from the framing constants, so keep the constants and the test generator in
  sync.
