## 3. Why `early_start`/`early_finish` are not separate keys (the one judgement call)

The MPP14 task row stores **six** date words in three pairs. W26/`manual-start-edit.json`
name the *fields* as:

```
+96  Start        +100 Finish        (Project's GetField raw "Start")
+104 EarlyStart   +108 EarlyFinish   (Project's GetField raw "EarlyStart")
+112 LateStart    +116 LateFinish    (Project's GetField raw "LateStart")
```

but Project's **COM properties** `Task.Start`/`Task.EarlyStart` report the
`+104/+108` word on a manual row as well (`manual-start-edit` before/after:
Start and EarlyStart are both 2026-01-04 13:00, then both 2026-01-12 08:00;
`GetField(Start)` stays at the stale `+96`). On every COM read-back on disk
`EarlyStart == Start` and `EarlyFinish == Finish`: **32/32** task rows in
`w3-o4.json` (all eight constraint types, feasible and infeasible, ALAP
included) and **4/4** in `w3-o1-open.json`, and the manual fixtures agree.

So the dump already carries the early pair exactly once, as `start`/`finish`
(the words Project reports for both properties). `calculated_start/finish` is
the `+96/+100` pair, which is the stored Start/Finish *field* (the calculated
copy for a manual row). Emitting `early_start` as `+104` would be a second key
with identical bytes; emitting it as `+96` would be wrong for the COM property
name. The new `late_start`/`late_finish` keys complete the six-word set without
duplicating either. If the coordinator wants the keys spelled `early_*` in the
schema, the change is a rename of `start`/`finish` (same bytes) and needs a spec
decision; it adds no comparison power.

## 6. What re-recording will change, and the one risk to watch

1. All eight oracles must be re-recorded (they are schema 1). No scenario JSON
   change: every scenario says `"compare": "all"`, `flatten()` is key-agnostic,
   and the field count grows automatically.
2. Expected new totals after re-record: `247, 247, 254, 247, 247, 247, 253, 209`.
3. **Late pair on auto rows is the new comparison, so it can surface a real
   engine/writer difference.** The applier writes the plan's late pair only
   when the row's dates move (E2's rule); otherwise it keeps the stored pair.
   On the manual scenarios our dumps keep synthetic-base's stored words; on
   `task-calendar` (auto rows on `synthetic-calendars.mpp`) our dump currently
   reports e.g. task 1 late 2026-01-05 09:00 / 2026-01-09 18:00, which is what
   our planner+writer produced. Whether Project's save recomputes a *different*
   late pair there is exactly what the re-record measures; if it does, that is
   a planner/writer gap, not a dump defect (the words are Project's LateStart/
   LateFinish fields, measured in §2).
4. The manual late pair is expected to keep matching: Project's own re-save of
   `base.mpp` (`resaved-base.mpp`) stores the same `+112/+116` words as the
   input, and E2 already measured that a manual row's late pair is the inverse
   of its boundary arithmetic (the applier keeps it deliberately).
