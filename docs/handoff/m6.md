## 1. Defect 1 — MPP12 in `tools/recalc`

### What was wrong

Nothing in the current `core/plan` or `tools/recalc` hard-codes a table root for
loading.  `tools/recalc/main.cpp` calls `mpp::load_file(path)`, and
`core/plan::from_mpp(document)` consumes the resulting `mpp::Document`; the
reader's `detect_format()` (reader.cpp) chooses `"112"` vs `"114"` from
`Props12`/`Props14` and the actual table storage, and stores it in
`Document::table_root`.  The failure the M5 report measured
(`no Task table: no stream '114/TBkndTask/FixedData'`) is the stale binary
`build\w62\tools\recalc\Release\recalc.exe` (built 06:50, before the wave-18/G1
MPP12 reader landed) linked against a pre-MPP12 `core_mpp.lib`.

### What changed

* `tools/recalc/main.cpp`: comments now say the calendar comes from the file's
  detected table root (`<table_root>/TBkndCal`, `<table_root>/Props`), and the
  header documents that reader/container warnings are printed on stderr.
* `core/plan/plan.cpp` (`attach_task_calendars`, one string, additive): the
  "uids are absent from 114/TBkndCal" note now uses `table.table_root`
  (`CalendarTable::table_root`, wave 19), so an MPP12 file says `112/TBkndCal`.
  This is the only `"114"` left in the plan/recalc load path that a caller sees;
  the rest are comments.  Kept to one line because E5 is editing this directory
  concurrently.
* No table loading was added: the reader already owns version/table-root
  detection and `Document` is the plan input.

## 2. Defect 2 — CFB FAT slack (`corpus/imported/sf248.mpp`)

### What was wrong

`core/mpp/cfb.cpp` had **no** "FAT covers N sectors but the file has M" check;
its FAT is sized by the FAT entries that actually exist, and `fat_next()` already
throws when a chain asks for an entry past that array.  The rejecting message in
`docs/import-corpus.md` §6/§7 item 3 is
`core/mppwrite/cfb_writer.cpp:376-380` (`CfbDocument::parse`), and
`tests/engine_diff_tests.cpp::dump_file` opens `mpp::load_file` *and then*
`mppwrite::CfbDocument::from_file`, so the dump tool rejects `sf248` even when
the reader accepts it.  (`core/mppwrite/**` is not this stream's ownership.)

So the reader-side work is the tolerant *reporting* the brief asks for, and the
mppwrite check is a named action for its owner (below).

### What changed

* `core/mpp/cfb.h/.cpp`: `CompoundFile` gained
  `std::vector<std::string> const& warnings()`.  `parse()` compares the physical
  sector count (`data_.size()/sector_size_ - 1`, the header sector excluded) with
  the FAT entry count and, when the FAT is shorter, records
  `"N unreferenced sectors: the FAT describes X of the file's Y sectors; the
  remainder is not part of any chain"`.  Nothing else changes: a chain that
  points at a sector with no FAT entry still hits `fat_next()`'s
  `FAT lookup for sector … is out of range` and the load throws.
* `core/mpp/reader.cpp` `parse_document()`: copies `cfb.warnings()` into
  `Document::warnings` **first**, before format/table warnings, so a caller (or
  `reader_dump --warnings`) sees the container fact before table damage.
* `tools/recalc/main.cpp`: prints `  reader warning: …` to stderr (stdout tables
  unchanged), capped at 20 lines plus `... and N more (reader_dump --warnings
  prints all)` because damaged real files carry hundreds (PROJECT_A 30, sf248
  280+).  This is what makes "expect a warning, not a rejection" visible without
  a `--warnings` flag.
* `core/mpp/reader.h`: document the slack rule in the file comment and note that
  `Document::warnings` starts with container warnings.

### Verification

`recalc corpus\imported\sf248.mpp` (stderr head):

```text
  reader warning: 191 unreferenced sectors: the FAT describes 768 of the file's 959 sectors; the remainder is not part of any chain
  reader warning: Calendar VarMeta header declares 3 entries but the stream holds 23; the stream wins
  reader warning: VarMeta repeats 6 (uid, key) pairs; the first offset for each is used
  reader warning: TBkndTask/FixedData is 8494 bytes = 48 + 202*n + 164; the trailing bytes are ignored
  ...
recalc: recalculation failed: error=no tasks recalculate: the task list is empty
```

* `191 / 768 / 959` are exactly the measured numbers (959 sectors, 768 FAT
  entries, 191 slack), not derived from the brief.
* Exit status is 1 for `sf248` only because it has **0 live tasks** (40 deleted
  task slots, assignments still present); it is not a CFB rejection.  Loading
  succeeds; the warning is emitted.
* `build\g1-reader-dump` (pre-change) also loaded the file; the new warning is
  the added signal.
* Still rejected by `engine_diff_tests --dump` via `CfbDocument`:
  `'…/sf248.mpp': FAT covers 768 sectors but the file has 959`.  **Owner
  action:** relax `CfbDocument::parse` the same way (short FAT is a warning; a
  chain past the FAT is fatal), or have the dump not open `CfbDocument` for a
  read-only dump.  This stream must not edit `core/mppwrite` or
  `tests/engine_diff_tests.cpp`.

### Regression tests added (`tests/mpp_error_paths.cpp`, synthetic, corpus-free)

* `test_cfb_unreferenced_sectors`:
  * builds the valid CFB, pads the FAT to whole sectors, appends 8 sectors no
    chain references, asserts the document still has its task and warns
    `8 unreferenced sectors` plus the `768 of the file's` count shape;
  * patches the directory chain's first FAT link to a sector that exists
    physically but has no FAT entry, asserts `mpp::Error` (not a crash, not a
    non-mpp exception) whose text names the FAT.
* `test_valid_control` additionally asserts a compact CFB reports no slack
  (no false positive).

## 3. Defect 3 — `SubprojectA-9/B-9.mpp` (the 206-byte MPXJ layout)

### Root cause (measured from the bytes)

Both files are `Props14` + `114/` containers (80 streams), but their Task table
is the MPXJ writer's layout, not Project's:

| file | FixedData | row stride | FixedMeta data offsets |
|---|---|---|---|
| `SubprojectA-9.mpp` | 872 = 48 + 206×4 | **206** | 48, 254, 460, 666 |
| `SubprojectB-9.mpp` | 1078 = 48 + 206×5 | **206** | same stride |

`FixedMeta` headers: 7 entries (4 rows + 3 descriptors) and 8 entries (5 rows +
3 descriptors) respectively -- so the 206-byte stride is what the file's own
metadata declares, and the 202-byte slice slipped 4 bytes per row (hence uid 0
repeats and the "48 + 202*n + 16" warning).  The fields are **not** MPP14
offsets (row 1's date-like words sit at `+8/+12` and `+64/+68`, duration at
`+60` is 524288, not ticks), and the same 206-byte/`48,254,460,666` signature is
the MPXJ-written MPP12 variant G1 documented in `docs/handoff/g1.md` §3.12
("a different record layout, not a shifted one").  Decoding it would be guessing
at an unmeasured layout.

### What changed

* `core/mpp/reader.cpp`: `detect_unsupported_task_stride()` runs before the
  202-byte slice.  It reads `FixedMeta`'s data-entry offsets and, when they are
  uniform, start at 48, consume FixedData exactly (`48 + stride*n == size`) and
  `stride != 202`, throws a positioned `mpp::Error`:

  ```text
  MPP14 Task table at 114/TBkndTask/FixedData holds 4 data rows of 206 bytes
  each (row 0 is the project row); the Project-2010+ layout this reader
  implements is 202 bytes.  The file may be an MPXJ-written MPP14 or a
  different variant; its record size is not guessed at.
  ```

  A uniform 202 stride, a metadata-less table, or irregular offsets (deleted
  slots) do not trip it, so Project files behave exactly as before.
* `core/mpp/reader.h`: documents the refusal next to the 202-byte row offsets.
* `tests/mpp_reader_tests.cpp::test_probe_fixtures`: the corpus sweep now skips
  `SubprojectA-9.mpp`/`SubprojectB-9.mpp` like it already skipped `*-from14.mpp`
  and **pins the refusal** on the real files (error raised, message names 206
  and 202).  `+4` checks (980 -> 984 with corpus; 335 -> still 335 with
  `MPP_NO_CORPUS=1`, the new checks are corpus-gated).
* `tests/mpp_error_paths.cpp::test_unsupported_task_row_stride`: synthetic
  206-byte table (FixedData 872, FixedMeta offsets 48,254,460,666) -> `mpp::Error`
  naming 206 and 202.  Corpus-free.

`recalc corpus\probe\SubprojectA-9.mpp` now exits 1 with that message (and
likewise B-9, 5 rows); it no longer reports "the task list is empty".

## 4. Behaviour changes a caller will notice

1. **`Document::warnings` can now start with a container warning**:
   `"N unreferenced sectors: …"` for a FAT-short file (`sf248`: 191/768/959).
   Files whose FAT covers every sector are unchanged (all committed fixtures and
   every Project-written corpus file we checked).
2. **`tools/recalc` prints up to 20 reader warnings** (`  reader warning: …`) on
   stderr, then an `... and N more` line.  stdout (TSV / `--compare` tables) is
   byte-unchanged; the M2 run still prints `overall 332 / 332`.
3. **MPP14 Task tables with a uniform non-202 row stride are refused** with a
   positioned `mpp::Error` instead of returning zero-uid/nonsense rows.  Only the
   two MPXJ-written subproject fixtures are known to be affected.
4. **MPP12 task-calendar note** now names `112/TBkndCal`; MPP14 still says
   `114/TBkndCal`.
5. `CompoundFile` has a new `warnings()` accessor (additive); `core/cal`,
   `app` and `core/session` share the container and therefore tolerate FAT slack
   without changes.

## 6. Verified vs inferred

**Verified in bytes / against the corpus**

* All three defects' observable behaviour: the 15-file MPP12 sweep above, the
  sf248 `191/768/959` warning, and the A-9/B-9 `206 vs 202` refusal with the
  offsets printed above (read directly out of the FixedMeta stream).
* `sf248`'s FAT slack is the only container warning on it; no chain walks past
  the FAT (load succeeds).
* M2 is unchanged at 332/332 (stdout tables identical; only stderr gained
  reader warnings).

**Inference / no oracle**

* That the 206-byte MPXJ layout is *not* decodable as a shifted MPP14 row is a
  structural conclusion (metadata offsets + field values that are not MPP14's),
  consistent with G1's MPP12 finding; no MPXJ source was read this wave.
* `sf248`'s 0 live tasks is this reader's liveness rule (every task row lacks a
  VarMeta group / is a deleted slot) and its 40 skipped rows; the brief only
  asks for tolerance, not for recovering that file's tasks.  MPXJ opening the
  file does not prove our row liveness is right -- see open items.
