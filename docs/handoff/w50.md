## 3. Measured container/record layout

Header (16 bytes), little-endian:

| offset | field | measured |
|---|---|---|
| +0 | `u32 size_word` | `stream_size - 4` for `114/Props` and `214/Props` |
| +4 | `u32 size_repeat` | same value |
| +8 | `u32 format word` | `0x00010000` on 114/214 and probe Props14 |
| +12 | `u32 declared_entries` | **not** a record count (see below) |

`Props14` is the exception: its first two words were `stream_size - 32` (probe),
`- 56` (corpus A) and `- 80` (corpus B). Corpus B's format word was
`0x0001006f` and `declared_entries` was 6,488,086. The parser therefore only
requires the two size words to agree, be >= 16 and <= stream size; it reports
the values without trusting the relationship. This is a measured correction to
the assumption "Props14 shares the layout": it shares the **record** layout, not
the header semantics.

`declared_entries` vs parsed records:

| stream | declared | records | tail |
|---|---|---|---|
| probe `114/Props` (formulas/prefs) | 262 | 161 | 85,408 |
| probe `214/Props` | 109 | 47 | 3,200 |
| probe `Props14` | 20/21 | 5 | 263 |
| corpus A `114/Props` | 290 | 175 | 86,156 |
| corpus B `114/Props` | 290 | 174 | 86,114 |
| corpus A/B `214/Props` | 115 | 53 | 3,200 |
| corpus A/B `Props14` | 22 / junk | 6 | 301 / 325 |

Records, back to back, no padding:

```
u32 payload_length
u32 id                 // byte 2 == 0x40 on every measured id
u32 kind               // 0 blob, 2 16-bit, 4 32-bit, 9 64-bit (8 bytes)
u8  payload[payload_length]
```

`id` families measured: `0x0240xxxx`, `0x0340xxxx`, `0x0440xxxx`,
`0x0b40xxxx`, `0x3540xxxx`. The parser stops at the first offset whose id does
not carry the `0x40` byte; that offset becomes the opaque tail. Record ids and
payloads measured on the probe:

- `0x35400016` kind 4, 4 B, value 4.
- `0x024003e8` kind 0, 316 B: UTF-16 comma-separated `TBknd...` table-name list.
- `0x02400008` kind 0: project name (28 B in the synthetic fixture; 32 B in the
  prefs baseline, 30 B in `prefs-col`).
- `0x02400029`, `0x024013c2`: 16-byte identity/GUID-like values.
- `0x02401390` kind 0, 568 B: custom-field formula table.
- two kind-9 records (`0x024001f`, `0x0240020`), 8 zero bytes each.

## 4. Formula result (the product goal)

`extract_formulas()` scans every kind-0 payload containing UTF-16 `MSPJ`, parses
the directory and returns:

```
u32 inner_size (== payload_length)
u32 count
count * { u32 field_id, u32 relative_block_offset }
blocks at payload_start + relative_block_offset
block = u32 13, u32 0xffffffff, 7 * u32 format words,
        UTF-16LE formula, u16 NUL, optional u32 trailer
```

Recovered from `tests/data/synthetic-props.bin` (all six, field id association
is the `CUSTOM` list in `scripts/oracle_w10.py`, so it is measured):

| field id | field | stored formula | block | text | 7 format words | trailer |
|---|---|---|---|---|---|---|
| `0x0b400033` | Text1 | `[MSPJ188743694] & "-" & [MSPJ188744967]` | 2786 | 2822 | `0x74` x7 | none |
| `0x0b400048` | Flag1 | `IIf([MSPJ188743712]>50,1,0)` | 2902 | 2938 | `0x5c` x7 | none |
| `0x0b400057` | Number1 | `[MSPJ188744967]*2` | 2994 | 3030 | `0x4c` x7 | `0x67` |
| `0x0b400058` | Number2 | `[MSPJ188744967]/480` | 3070 | 3106 | `0x4c` x7 | none |
| `0x0b400067` | Duration1 | `[MSPJ188744967]/2` | 3146 | 3182 | `0x4c` x7 | `0x72` |
| `0x0b400109` | Date1 | `[MSPJ188744965]+7` | 3222 | 3258 | `0x4c` x7 | `0x30` |

Oracle source formulas, in the same per-field association: `[Name] & "-" &
[Duration]`, `IIf([% Complete]>50,1,0)`, `[Duration]*2`, `[Duration]/480`,
`[Duration]/2`, `[Start]+7`. `[MSPJ<decimal>]` is the decimal field id:
`188743694 = 0x0b40000e`, `188744967 = 0x0b400507`, `188743712 = 0x0b400020`,
`188744965 = 0x0b400505`.

All six are also present in `w10-formulas2.mpp`/`w10-formulas3.mpp`; their block
and text offsets are +2 from the table above only because the project name is two
bytes longer. **No extra fixture is needed for the association.** If a future
stream wants wider coverage, the cheap fixture is a synthetic project with
formulas on Number3/Text2 and the same save; the decoder does not hard-code
`0x02401390` (it finds the record by the MSPJ payload).

`props_report --formulas` prints, for example:

## 5. Table / view definition work (and an oracle correction)

The brief asked for table definitions in `114/Props`. The bytes do **not**
support that premise, and this is the honest result:

1. **No table names.** The prefs fixtures contain exactly three UTF-16 runs:
   the `TBknd...` table-name list, the project name, and `Standard`. There is no
   `Entry`, no column-name list, no field-id list associated with a table.
2. **The `114/Props` -2 B oracle delta is the project name.** The record
   `0x02400008` payload goes 32 -> 30 B when the file is renamed
   `w10-prefs-base` -> `w10-prefs-col`, and back to 32 B for `-date`. That is
   the whole file-size change. The other changed bytes are the two identity
   records and the tail.
3. **The date-format change is isolated to one tail word.** Aligning the
   fixed 85,408-byte tail (start 3302 for base/date, 3300 for col):

   | comparison | changed tail words (offset relative to tail) |
   |---|---|
   | base -> column added | key `0x02000001` value 0 -> 2 at +28; one word 168 -> 208 at +60,176 |
   | base -> `DateFormat=5` (col -> date) | key `0x00010001` value 298 -> 332 at +60 only |
   | base -> date (both edits) | all three words above |

   The typed tail prefix is six `[u32 4][u32 key][u32 4][u32 value]` groups
   (tail+0..+95), then a 7-word/28-byte field-reference array at tail+112
   (1,312 entries in the synthetic fixture: first ids `0x0b400017`,
   `0x0b400056`, `0x0b400062`, `0x0b40009f`, `0x0b4000f7`, then a sorted
   catalog `0x0b400000..0x0b40059d`; one 40-byte gap). The values 298/332 are
   not the literal format 5, so this is an offset/size-like value, **not a
   proven date-format code**. The API exposes the key/value pairs and the
   field-reference entries; both are documented as inferred semantics.
4. **`Props14` +192 B is a path string, not table state.** In the prefs
   fixtures the record `0x35400008` grows from 18 B to 196/198 B because it
   holds a long recent-file path (not reproduced here). W46's "Props14 +192"
   delta must not be read as a table-column payload.
5. **`214/Props` is size-stable (13,102 B)** across the three prefs fixtures.
   Its real table/view content is under `214/` (`CTable`, `CV_iew`, ...) and
   was not decoded here. If the app later persists table/view settings, that is
   a `214/` stream task, not a `114/Props` task.

So the deliverable "table definition region" is reported as: **not present as a
named table definition in `114/Props`**; the only correlated region is the
opaque tail and its typed prefix. The decoder does not overclaim a table writer.

## 7. What is measured vs inferred

Measured: header/record framing on 6 probe + 4 corpus streams; id families and
kinds; the record payloads above; formula directory, six formulas, field ids,
offsets, format words and trailers (three fixtures); tail sizes; typed-prefix
keys/values; field-reference array stride (28 B, one 40 B gap), first ids and
count; the prefs diff bytes and exact offsets; the `Props14` header exception
and corpus B's junk header fields.

Inferred: kind -> integer-width naming; the semantic meaning of the tail typed
keys and of the `0x00010001`/`0x02000001` values; the "field reference" meaning
of the 7-word tail entries; that `0x02400029`/`0x024013c2` are identity values.

## 9. Traps

- `declared_entries` is not a record count (262 vs 161 on the probe). Never loop
  on it.
- `Props14` is not `size-4`; corpus B's format/declared words are junk. Parse
  records; do not trust header fields without per-variant evidence.
- Formula blocks have an optional trailer; use the UTF-16 NUL, not a fixed
  stride. A damaged block drops to five formulas (tested).
- `utf16_preview` returns hex for binary payloads (e.g. the formula record) and
  for one-code-unit non-ASCII blobs; don't parse the preview.
- `field_references` is a scan, not a schema: it requires `0x0b40xxxx` and a
  plausible length word, and the entry meaning is inferred.
- Do not write `114/Props`. Do not copy the `Props14` path string into docs or
  tests (it is a host path, not table data).
- `WAVES.md` had no "Wave 11" section on disk when this stream ran (it ends at
  the wave-10 results); the brief's wave-11 text is the authority used here.
