## 3. What is left, and why

1. **`file.*` (`file stream <path>` size) — 8–10 per scenario.** Our save of the
   recalculate-only scenario now changes *no bytes* (the fixture already holds
   the correct state), while Project's save rewrites/grows
   `114/TBkndAssn/Var2Data|VarMeta`, `214/CEdl/Var2Data`, `214/CFilter/*`,
   `Props14` (and `?DocumentSummaryInformation` on operation scenarios). A
   size comparison can never pass. **Note for the coordinator's change-set
   proposal:** our set of changed streams is then empty for `recalculate`, which
   will still differ from Project's; the file family needs either a writer
   stream that reproduces Project's churn or a spec decision to exclude it for
   operation scenarios.
2. **`constraint-mso` `task 3 duration_ticks` 9600 vs 12000.** Setting MSO on the
   manual row made Project rewrite the stored Duration to 12000 while its own
   calculated span stayed 9600 (2 d). 12000 is the kept Finish − Start counted
   with a full finish day (240 + 480 + 480), i.e. an edit-time recompute of the
   duration word, not a scheduling rule; the engine has no such rule and the
   dump compares the stored word. Left as the one measured difference, per the
   "save-churn rather than semantics" instruction.
3. **`assignment-50pct` placeholder row.** `Task.Assignments.Add` on Project
   tombstones the live null-resource placeholder of the same task (measured, see
   `core/mppwrite/add_delete.h`); the added row (uid 4) already matches. Our
   `add_assignment_row` deliberately leaves the placeholder, so ours still has
   assignment 1. A `delete_assignment_row` call for that placeholder in the
   applier's add_assignment handler would close it (Project's measured
   behaviour), not done here.
4. `task-calendar` remains unrecorded (needs a fixture with a second named base
   calendar; `Project.Calendars` does not exist in this build).
5. Manual rows with actuals, an elapsed duration, a task calendar or a deadline
   have no oracle row; the bridge falls back to the CPM path and counts them in
   `PlanResult::manual_unpinned`.

## 6. Traps hit

* The scenario applier performs TWO saves (`recalculate` then `save`). Any plan
  value that is not idempotent across them trips `core/mppwrite`'s single-copy
  refusal; that is why `TaskValues::manual_dates` exists and why the applier
  recalcs-and-persists after structural edits.
* A manual row's +112/+116 are the inverse of its boundary arithmetic (that is
  why `StartSlack == TotalSlack`); the planner does not compute that inverse, so
  the applier keeps the stored late pair for manual rows (not compared by the
  dump).
* Dropbox mtime churn makes `edit` fail minutes after a read; re-read and retry
  (happened ~20 times). PowerShell has no heredoc; helper patches live in
  `build\e2\patch_*.py`.
