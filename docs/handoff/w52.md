## 1. What is done

### 1a. Link rows (`core/mppwrite/add_delete.h/.cpp`)

`add_task_link(doc, predecessor_uid, successor_uid, type, lag_ticks, path)` and
`delete_task_link(doc, link_uid, path)`.

The coordinator's `w12-linkadd.mpp` (synthetic-base + two COM links) settled a
design question the original brief left open: a link add writes **FOUR**
`114/TBkndCons` streams, not two. Measured shape (also confirmed on
`corpus/probe/link1.mpp`, `w11-linkdelete-pre/-post.mpp`):

| stream | size | contents |
|---|---|---|
| `TBkndCons/FixedData` | `20 * n` (no header) | uid +0, pred +4, succ +8, u16 type +12 (0 FF, 1 FS, 2 SF, 3 SS), i32 lag ticks +14, u16 lag format +18 (7) |
| `TBkndCons/FixedMeta` | `16 + 10 * n` | one entry per row: +0 state, +2 field count 0, +4 row byte offset, +8/+9 = `dd 00` |
| `TBkndCons/Fixed2Data` | `48 * n` | three 16-byte identities per link: link id, predecessor task id, successor task id |
| `TBkndCons/Fixed2Meta` | `16 + 9 * n` | one 9-byte entry per row: +0..3 = 0, +4 = record offset (`row * 48`), +8 = 0x0f / 0x07 |

Headers (both metas): magic `ba ad df fa`, +4 = 4 with no tombstone, +8 = entry
count, +12 = FixedData/Fixed2Data byte size. `VarMeta` (24-byte empty header) and
`Var2Data` (0 B) exist and are never touched.

`add_task_link` appends one row and all four companion records. Link uid =
largest uid in the whole table (tombstones included) + 1 (empty table -> 1).
It refuses: an unusable output path; predecessor/successor uid 0; a self-link; a
uid with no LIVE task row (unknown, tombstoned, or no VarMeta group); a task row
with an all-zero Task/Fixed2Data identity; type outside 0..3; a lag outside
`+/-kMaxLinkLagTicks` (175,200,000 ticks -- a writer policy bound, explicitly not
a measured Project limit); a live duplicate `(pred, succ, type)` (the lag is not
part of the relation; a tombstoned row does not block a re-add); and a damaged
Cons table (wrong stream sizes, stale +8/+12 words, magic mismatch, a row with
other than exactly one FixedMeta entry, an entry state other than 0x00/0x02).

`delete_task_link` is the same tombstone contract W48's task cascade uses:
FixedMeta entry `+0 = 0x02`, `+2 = 0`, header `+4 |= 0x02`; every size stays and
FixedData/Fixed2Data/Fixed2Meta are byte-identical (Project's own
`w11-linkdelete-post.mpp` does exactly this to both of its link rows). It refuses
uid 0, an unknown uid, an already-tombstoned row and a damaged table.

Both entry points validate everything before touching the output, apply to a copy,
write, re-open from disk, prove the built bytes, prove only the intended streams
changed (214/ included), and replace `doc` with the re-read document.

**Task-table validation is deliberately narrow for an add.** Project's own
`w12-linkadd.mpp` declares 38 VarMeta entries while the array holds 42 -- the same
stale-count save shape Project leaves on its add/delete files. A link write never
touches VarMeta, so `add_task_link` checks only Task FixedData `48+202*n`,
FixedMeta `16+47*(n+3)`, Fixed2Data `64*(n+3)` and VarMeta's 24+12*n geometry, not
its declared count. This deliberately differs from `validate_table` (which W45's
`add_task_row` still uses because it DOES edit VarMeta). The test proves it on
Project's own files: it appends a third link to `w12-linkadd.mpp` and deletes
link uid 3 from `link1.mpp` (4 live links remain), re-reading both from disk.

**Link identities (the one non-measured degree of freedom).** Every 16-byte id in
a file shares bytes 4..15; byte +3 is the varying part. Project's own values come
from a file-global counter we have not identified (link1: link ids 0x58..0x5c
after task ids 0x41/0x50/0x52/0x54/0x56; w12-linkadd: link ids 0x12/0x13 after
task ids 0x09..0x0c). W52 copies the endpoint ids byte-for-byte from the two task
rows' Task/Fixed2Data records, and derives the link id deterministically: the
first non-zero task identity as template, with byte +3 set to the lowest value in
1..255 not used by any identity of the same GUID family anywhere in the file
(all `*/Fixed2Data`, every 16-byte slot). This guarantees uniqueness and
determinism without inventing Project's counter. **Project acceptance is the
gate's job to confirm**; the fixtures carry link ids `ba cb 09 01` / `ba cb 09 02`
(endpoint ids are synthetic-base's `b0`, `b2`, `b4`).

**Fixed2Meta +8** is 0x0f for the first live link naming a successor and 0x07
for a later one. This is an inference from link1 (rows 0..2 first, rows 3..4 the
second links into successors 3 and 4) and w12-linkadd (both first). It is applied
over live rows only.

### 1b. Custom-field clear (`core/mppwrite/field_values.h/.cpp`)

`clear_field_value(doc, uid, field_id, path)` stores the measured EMPTY value and
clears every presence store. Defined semantics (there is no measured Project
field-delete encoding):

| kind | VarMeta payload written | presence store cleared |
|---|---|---|
| Text | `00 00` (empty UTF-16LE + NUL) | FixedMeta entry `+21` bit 0x20 |
| Number | 8 zero bytes (f64 0.0) | `+25` bit 0x08 / 0x10 |
| Duration | 4 zero bytes (u32 0) | `+26` bit 0x01 and `+27` bit 0x20 |
| Date | `ff ff ff ff` (`kInvalidDate`) | `+29` bit 0x40 |
| Flag1 | none (it is not VarMeta) | FixedMeta `+24` bit 0x02 **and** Fixed2Meta mirror `+31`/`+61` bit 0x80 |

The VarMeta entry is KEPT and repointed at the new empty block, so FixedMeta `+2`
(the row's exact entry count) is unchanged and the old block is orphaned -- the
same append-only shape `save_field_values` uses. `114/TBkndTask/Props` and
`114/TBkndAssn/Props` are never written: the field stays registered (measured
W48 behaviour: Project keeps the definition). A field that was never stored gets
no new entry; clearing an already-empty field is a byte-identical no-op (the
all-or-nothing re-read still runs).

Refusals: an unusable path; uid 0 or a uid with no live task row; any field whose
storage is unmeasured (Cost) or whose FixedMeta tail-presence bit is unmeasured
(Flag2..Flag20 and every id outside Text1/Flag1/Number1/Number2/Duration1/Date1);
a damaged Task table. `save_field_values` itself was not changed.

## 5. Open items

   attack in this order: (a) the link identity values (copy Project's counter

2. **Real field-delete shape.** `clear_field_value` keeps the VarMeta entry and
   the Props registration, so `FixedMeta +2` does not change. A fixture where
   Project clears a previously-set Text1 would show whether Project removes the
   entry and decrements `+2`; until then our semantics is the documented one.
3. **Elapsed lag.** `lag_format` is written as 7 (working days). `core/mpp` can
   read format 8 (elapsed days) but the writer has no API for it.
4. A future task-delete path could call `delete_task_link` per dependent row
   instead of duplicating the entry tombstone in the cascade; both already share
   the same header-bit contract.

## 6. Traps hit here

- `TBkndCons/FixedMeta` is `16 + 10*n` with n = ROWS, one entry per row; there is
  no 48-byte FixedData header and no rows+3 padding. `Fixed2Meta` entries are
  9 bytes (`16 + 9*n`), not 10.
- An empty Cons table still has 16-byte FixedMeta and Fixed2Meta streams. The
  shared `load_dependent_table` used to return for 0 rows before reading the
  header; W52 moved the 0-row return after the meta read.
- `mppwrite`'s filtered ctest includes every writer test: build the pre-existing
  seven targets in the same build dir or ctest reports them "Not Run".
- The field-values whole-file FNV depends on `Props14` (save metadata). Compare
  per stream when claiming `save_field_values` is unchanged.
- Dropbox mtime churn: the edit tool intermittently reports "file changed since it
  was read" even with no other writer; re-read immediately before each edit and
  make one edit per read (`memory/writer.md` W45 trap).
