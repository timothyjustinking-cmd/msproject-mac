## 1. What is done

### Custom-field editing (deliverable 1)

`Edit ▸ Task Fields…` opens one modal form for the six measured fields the reader
decodes — **Text1, Number1, Number2, Date1, Duration1, Flag1** — prefilled from
`Task::custom_fields` through the app's display mapping (date and duration
preferences included, flags `Yes`/`No`). On OK the form is parsed and queued as
pending edits; Save writes them through `mppwrite::save_field_values` (one file for
all set values) and `mppwrite::clear_field_value` (the measured empty-value shape,
one call per cleared field). A blank field clears; a blank on an absent value queues
nothing; an unchanged value queues nothing; one invalid field refuses the whole form
and names the field. Validation follows the writer's types exactly: finite `double`,
valid packed date word, duration in file ticks (COM minutes × 10; `4800` = one 8-hour
day), `Yes`/`No`. The grid columns stay read-only; the dialog is the only writer.

The whole dialog decision logic is portable C++ in **`app/field_link_edits.h/.cpp`**:
`task_field_specs()`, `field_value_text()`, `make_task_field_edits()` (uses
`core::sheet::parse_edit_text`, so the forms are the sheet's own: `3d`,
`2026-10-26`, `Yes`), plus the push/display rules in `app/edit_model.cpp`.

### Link editing (deliverable 2)

`Edit ▸ Predecessors…` lists the selected task's incoming links (predecessor ID,
name, type `FF/FS/SF/SS`, lag, `(pending)` for a not-yet-written add) and lets the
user **delete** one file link and/or **add** one (predecessor ID + type + lag) in the
same OK. Lag syntax: `0`, `2` (bare = working days), `2d`, `-1d`, `4h`, `30m`
(case-insensitive `d`/`h`/`m`; 4800 ticks/day, 600/hour, 10/minute). Refused before
queueing: pred == self, unknown endpoint, a pending-insert endpoint, a pending-deleted
endpoint, and a duplicate `(predecessor, successor, type)` (the writer's relation
identity; the lag is not part of it). `make_link_add` validates against the display
plan **with the pending delete applied**, so "delete this relation, then add it back"
works.

Save applies **link deletes → link adds → task deletes → task inserts → field values
→ start dates**, all on one document. `app::save_structural_edits` was extended; the
fixed order and the writer mapping live in `app/edit_model.cpp`. The link table is
`114/TBkndCons`; the writer allocates the link uid/identity and the app reloads the
file, never patching it.

**Atomicity.** Every writer call writes a file. All but the LAST write
`<target>.w51-structural-tmp`; the last writes the target. An earlier refusal removes
the intermediate, stops the cascade, and never creates/modifies the target. The source
is never written: `target == source` is refused unless the app itself wrote and
reloaded that file (same rule as wave 12).

### Undo/redo, dirty state, status (deliverable 3)

There is **one stack** (`app::StructuralEdits`), now holding six edit kinds: insert
task, delete task, set field, clear field, add link, delete link. It sits beside the
sheet's cell-edit history with the wave-12 rule unchanged (a queued edit ends the
cell history; a cell edit clears the structural redo list). Cmd-Z/Cmd-Shift-Z undo/redo
the queued field/link edit and rebuild the display plan, which shows the field value
or link immediately. `plan_is_dirty()` is `!edits.empty() || start edits`, so a pending
field/link edit lights the edited dot, is named in the status line
(`pending: N insert(s), N delete(s), N field edit(s), N link edit(s)`), in the close
prompt, and reaches a file only on Save. The status line after each dialog names
exactly what was queued (`Text1, Flag1 (clear)` / `2 add(s), 1 delete(s)`).

### Menus / preferences (deliverable 4)

`menu_model`: two new actions, `task_fields` (`Task Fields...`) and `predecessors`

## 7. Traps (do not re-learn these)

- **`core::gantt::LinkType`'s enumerators are `finish_to_finish` / `finish_to_start` /
  `start_to_finish` / `start_to_start`** (order FS/SS/FF/SF), not `finish_finish`.
  The FILE order is FF=0/FS=1/SF=2/SS=3, so the writer needs
  `writer_link_type()` (an explicit mapping, never a cast). The reader maps the other
  way in `reader_adapter.h`.
- **`mpp::FieldKind` != `mppwrite::FieldKind`** (same layout, separate enums);
  `FieldValue::kind` needs `writer_field_kind()`.
- **`core/mpp` lists a custom-field VarMeta entry regardless of its presence bit**, so
  after a clear the reader reports empty values, not absence. Do not assert
  `custom_field() == nullptr` after a clear.
- **`synthetic-base.mpp` has 0 link rows and 3 assignment rows.** The link tests start
  from zero links; do not "fix" the fixture.
- **One pending stack, one save order.** A task delete prunes the field edits and link
  adds naming it; a link delete stays (it runs first). Reordering the writer cascade
  would break "target written only last" and the delete-then-add semantics.
- **The edit/write tools race Dropbox's mtime churn on this folder** ("file changed
  since it was read"). Re-read immediately before an `edit`; for multi-anchor changes
  use a throwaway Python script under `build\vs-w55\` with a `count == 1` assertion per
  anchor before writing anything.
