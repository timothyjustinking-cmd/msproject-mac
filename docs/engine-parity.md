# Engine and backend parity — differential testing against MS Project**Requirement (2026-10-23).** The engine and backend, like the UI, must be*identical to MS Project on this machine*. That is a behavioural claim, so it hasto be measured by running the same inputs through both and comparing everyobservable — not by "we implemented the algorithm".MS Project is installed here and is the only authority. Where our specificationand Project disagree, Project wins (`docs/coordination.md`).## What "identical" means, observablyFor a scenario (a base file plus an ordered list of operations), compare a**canonical state dump** produced from the file Project saved and from the fileour engine wrote. The dump is numbers and ids only, never names:| family | fields compared ||---|---|| task | uid, id, outline level, summary/milestone/active/manual flags, duration ticks, start, finish, early/late start and finish, free/start/total slack, critical, percent complete, constraint type + date, deadline, task type, effort-driven, work, cost || assignment | uid, task uid, resource uid, units, work, start, finish, contour/step count || resource | uid, type, max units, standard/overtime rates, calendar uid, cost || calendar | base calendar, work week, every exception (type, dates, occurrences, period, weekdays, month position/item/day) || project | start/finish, calendar, critical slack limit, currency, default task type || file | which streams changed, and stream sizes (not bytes — identity values churn) |A scenario **passes only if every compared field matches exactly**. A tolerancewould hide the class of bug this exists to catch (off-by-one ticks, wrongcalendar boundary, missed rounding).## How it runs* `tests/scenarios/*.json` — the scenarios: base fixture name, operations  (edit/insert/delete/link/constrain/recalculate/save), and the fields to compare.  Committed; ids and numbers only.* `scripts/engine_diff.py` — two halves:  1. **Oracle half** (coordinator only, `--record`): opens the scenario in MS     Project through `scripts/oracle_lock.py`, applies the operations with COM,     saves, and dumps the canonical state of Project's own result to     `tests/data/scenarios/<name>.oracle.json`.  2. **Ours half** (`--check`, CI-safe): applies the same operations through our     engine, writes the file, dumps the same state, and diffs it against the     recorded oracle state. Exit non-zero on any difference.* `docs/engine-parity.md` (this file) carries the current score: scenarios  passing / total, and the open differences with the instruction that reproduces  each.Scenarios are grouped by family so a wave can close one family at a time:scheduling, calendars, fields/values, links, resources/assignments, file format.## Where we already standThe existing gates are single-scenario versions of this idea and must keeppassing: **M2 332/332** (83 tasks × start/finish/slack/critical against Project'sown recalculated file), schedin 20/20 + 10/10, `plan_recalc` 291, `cal` 553,reader 685, assignments 679, links 773, add_delete 760, field_values 802,formula 1,249, viewstate 361. The writer is already byte-identical to Project'sown rows for task/link/resource/assignment adds and deletes, and Project displaysour custom-field values.What those do **not** cover, and this harness exists to find: task-type andeffort-driven interactions, constraint semantics (all eight, with deadlines andALAP), elapsed durations mixed with calendars, task and resource calendars,splits and contour shaping, cost accrual and earned value, material resources,multiple baselines, summary rollup corners, inactive tasks, and MPP12/14variants.## Honest scaleMS Project's scheduling engine is twenty years of accumulated behaviour,including leveling, contouring, cost accrual and earned value. "Identical oneverything" is a large programme: the realistic path is a growing scenario corpuswhose score is published, closing one family per wave, with the gaps named ratherthan assumed away. A family counts as done only when its scenarios pass and thefamilies it touches stay green.## Rules this harness must keep1. **Project wins.** A difference is a bug in our engine until shown otherwise;   then the specification is wrong and gets corrected with the evidence.2. **No tolerance.** Exact equality per field, or the scenario fails with the   field, the two values and the reproduction command.3. **No client data.** Scenarios use synthetic fixtures; recorded oracle states   carry ids, dates and numbers only.4. **The oracle half stays coordinator-only** (COM); the recorded JSON is what CI   compares against, so CI needs no Project.## Measured baseline (wave 17, 2026-10-23)The harness now exists as code. **No oracle state has been recorded yet**, so thescore below is a baseline of the machinery, not a parity claim.
