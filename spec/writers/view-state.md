# View-state persistence: sort, applied table, outline level, zoom

_Wave 35 group G2, 9 November 2026. Sources: the committed save pairs
`wave35-viewstate-*` (each a control, Project's edit save and a null save of the
control), the pair reports under [`evidence/`](evidence/) (generated by
`scripts/pair_anatomy.py`), and the COM oracle `scripts/oracle_w35_viewstate.py`
(neutral root `C:\w35\`, `scripts/oracle_lock.py`, `neutralise()`). Rows are named by
UniqueID throughout. Each section ends with its capability matrix: the shapes a
writer or edit-model path is enabled for, and everything else is refused up front._

## 1. Sort (W35-2.1): enabled for one Name or Duration key

Pairs: `wave35-viewstate-sort-name-desc`, `-sort-name-asc`, `-sort-duration-desc`
(enabled), and `-sort-two-keys`, `-sort-flat-name-desc` (evidence only). The base is
the five-task, two-level project (outline levels 0 and 1; UniqueID 1 is a summary over UniqueIDs 2 and 3;
UniqueIDs 4 and 5 are top-level leaves), Outline = True, Renumber = False.

### 1.1 Where a sort lives

A sort changes two streams (plus the `Props14` edit marker); no task stream, UniqueID
or ID moves (Renumber = False).

| stream | change |
|---|---|
| `214/CV_iew/Var2Data` | the sort specification inside the uid-2 view block (section 1.2) |
| `214/CEdl/Var2Data` | the displayed row order, as three records (section 1.3) |
| `Props14` | the edit marker (`core/mppwrite/edit_marker.h`), as on every editor save |

The null save of each control has per-save noise in `214/CEdl/Var2Data` (a save-path
record, id `0x26400031`, differs between saves of the same file) and in `Props14`; the
compare normalises that record, so only the edit's own bytes remain as effects.

### 1.2 The specification (`214/CV_iew/Var2Data`)

`Var2Data` is a sequence of `u32 length + payload` blocks. The block of view uid 2 / key
`0x20400006` starts at offset 42,576 and holds 42,692 payload bytes in every control.
The sort is stored **twice**, at block + 40 and block + 1,192, each copy 18 bytes: three
6-byte slots of `u32 field id, u16 ascending`.

| state | one copy (hex) |
|---|---|
| default (ID, ascending) | `17 00 40 0b 01 00 ff ff ff ff 01 00 ff ff ff ff 01 00` |
| Name descending | `0e 00 40 0b 00 00 ff ff ff ff 01 00 ff ff ff ff 01 00` |
| Name ascending | `0e 00 40 0b 01 00 …` |
| Duration descending | `07 05 40 0b 00 00 …` |

Field ids: ID `0x0b400017`, Name `0x0b40000e`, Duration `0x0b400507`. Descending is 0,
ascending 1. Both copies change identically: 4 bytes differ from the default per
copy-pair for Name descending (2 per copy), 2 for Name ascending (1 per copy), 6 for
Duration descending (3 per copy). The two-key pair additionally writes slot 1 (Duration
ascending, `07 05 40 0b 01 00`); its secondary key never decided a row on this project,
so it is not claimed.

The rest of the uid-2 block is untouched by a sort. The writer pins it: FNV-1a 64 of the
block payload with both 18-byte regions zeroed is `0xb2a54e044baa30a2`, so a file whose
view differs anywhere else is refused rather than guessed at.

### 1.3 The displayed order (`214/CEdl/Var2Data`)

Header: 20 bytes (`u32` stream length − 4, two equal size words, format `0x00010000`,
`u32` item count), then items `u32 length, u32 id, u32 kind = 1, payload`, one pad byte
when the length is odd. A sort rewrites three records:

| record id | payload | rewritten |
|---|---|---|
| `0x26400035` | 32 B: N UniqueIDs, then `0x000ffdc0, 0, 0` | the first N dwords: the displayed order |
| `0x26400036` | 4 B | the first displayed UniqueID |
| `0x26400024` | 64 B: N UniqueIDs, then `0xffffffff` fill | the displayed order again |

Measured at N = 5 only: `1 2 3 4 5` becomes `5 4 1 3 2` for Name descending (Task E,
Task D, Task A, then A's children C, B) and `4 1 2 3 5` for Duration descending; Name
ascending leaves `1 2 3 4 5` (the 0x35/0x36/0x24 words are unchanged, so the pair has
no CEdl effect). The `0x2640003d` record carried by four controls is untouched.

### 1.4 What the sort compares (pins)

The pairs fix the order for the measured names and durations only. The edit model
(`app/edit_model.cpp`, `sort_plan_order`) pins:

- **Siblings only** (rows under one parent, from the outline level); a child stays
  under its summary.
- **Name:** every sibling pair must differ at a first position holding two ASCII
  letters of the same case, neither name a prefix of the other. Project's collation of
  case, digits, punctuation and accents is not measured, so any other sibling pair
  is refused.
- **Duration:** sibling durations must be pairwise distinct (ties are not measured);
  a summary's duration is its stored duration.
- Row count 5 (the `0x35` payload length is N + 3 dwords, measured at N = 5).

### 1.5 Capability matrix

| shape | state | where it is refused |
|---|---|---|
| one key: Name ascending, Name descending, Duration descending | **enabled** | — |
| two keys | refused ("exactly one key") | `make_sort_edit`, `save_view_sort` |
| ID / Start / Finish / any other key | refused (one reason each) | both |
| Outline = False ("Keep outline structure" off) | refused | both |
| Renumber = True | refused | both |
| view uid other than 2, or a project whose applied view is not the measured block | refused | writer (digest, view uid) |
| row count ≠ 5, pending task, unpinned names or durations | refused | edit model; writer for the count |
| Duration ascending, or an ascending key whose order differs from the file's row order (only Name ascending, which moves no row, is measured) | refused ("Duration ascending is unmeasured", "an ascending sort that moves rows") | edit model, `push()` and writer |
| an outline other than 0-based levels 0, 1, 1, 0, 0 (a three-level, flat or re-nested one), from the plan and from the file's +172 words | refused ("sort one outline") | edit model and writer (`sorted_order_of`) |
| a file that already carries a sort or a different order | refused ("already carries a sort") | writer |

`wave35-viewstate-sort-flat-name-desc` (Outline = False) saves the same bytes as the
Outline = True pair on these five rows, so the option's effect is unmeasured and only
Outline = True is claimed.

The shell (`app_qt/main_window.cpp`, `apply_sort_choice`) queues the edit for a single
Name key and applies the session sort either way; every other dialog choice stays a
session sort with the specific reason on the status line. The Sort dialog does not offer
Duration, so a Duration sort is reachable through the edit model only. The reader does
not yet restore a persisted order on open (the plan stays in ID order); that is a
read-side gap, not a write-side one.

### 1.6 Gates

`mppwrite_roundtrip_viewstate_sort` (core, three pairs field by field through
`compare_all`, structural checks, every writer refusal with its needle),
`app_edits_sort` (edit model and cascade against the same pairs, every edit-model
refusal) and `qt_sort_persist` (the shell). Mutation checks and gate logs are recorded
in `docs/handoff/wave35-complete.md`.

## 2. Applied table (W35-2.2): NOT ATTEMPTED, a scope decision (R35G2-8)

Pairs: `wave35-viewstate-table-cost`, `-table-schedule` (`Application.TableApply` on the
five-task base, applied table Entry before). Reports: [`evidence/wave35-viewstate-table-cost.md`](evidence/wave35-viewstate-table-cost.md),
[`evidence/wave35-viewstate-table-schedule.md`](evidence/wave35-viewstate-table-schedule.md).

### 2.1 What applying a table changes

Both pairs change the same streams; no task stream moves.

| stream | change |
|---|---|
| `214/CTable/Var2Data` | 1,051 → 2,102 B: a second 1,047-byte table-definition block is appended (u32 length + payload), the Entry block untouched. The new block is Project's built-in definition of the chosen table (first column "Task Name" in both) |
| `214/CTable/FixedData` | 230 → 460 B: a second table row |
| `214/CTable/FixedMeta`, `VarMeta` | 26 → 36 B and 36 → 48 B: one more entry each |
| `214/CV_iew/Var2Data` | the uid-2 view block holds the applied table's name as UTF-16 and is re-laid out: 100,178 → 100,176 B for Cost (name 5 → 4 characters, Entry → Cost, −2 B) and → 100,184 B for Schedule (5 → 8 characters, +6 B); every later byte shifts |
| `214/CV_iew/VarMeta` | the view block's length and the offsets after it are re-pointed |
| `214/CEdl/Var2Data` | the applied-table name record is rewritten with the new name; the stream length changes by the same delta |
| `214/CEdl/VarMeta`, `214/Props` | derived lengths: the CEdl stream length (see 3.3), the CTable Var2Data length (`1b 04` → `36 08`, u16 at 10,738), the CV_iew Var2Data length low byte, and a table count (`01` → `02` at 10,690) |
| `Props14` | the edit marker |

### 2.2 Why it is not written

The effect is not a rule over the plan. The 1,047-byte definition blocks are Project's
own built-in tables, fixed-size structures whose column list, widths, titles and
alignments are not derivable from the project; a writer would paste two constants
copied from the pairs and re-lay a 100 KB view block around a name whose length
changes, with one measured name pair per table. Under the standing rules a command is
enabled only for a shape a port save reproduces field by field with a rule behind it;
here the only rule is "replay these two blobs", and the view-block re-layout (offset
re-pointing in `CV_iew/VarMeta` and shifted tails) was measured at two lengths only
(−2 and +6). Replaying it would claim every other table, name length and view layout
that has not been measured.

### 2.3 Capability matrix

| shape | state |
|---|---|
| applying any table to a task sheet | **refused** for the file (the shell lists only tables the file already stores and applies one to the session view, status "(session only)"; nothing is queued, so File > Save never writes a half-applied table) |

Pairs still needed to enable it: one pair per built-in table to be supported (the
oracle `table-<name>` pairs are one call each), a second measured name length per table
for the view-block re-layout, and the table-definition layout decoded to the field.

## 3. Outline level (W35-2.3): enabled for Show Level 1 and 2 on two measured outlines

Pairs (`Application.OutlineShowTasks`, each with a null save): `wave35-viewstate-outline-level1`
and `-level2` and `-all` on the five-task base (levels 1, 2, 2, 1, 1 in Project's 1-based
terms; 0, 1, 1, 0, 0 below), and `-deep-level1` and `-deep-level2` on a six-task three-level
outline (0, 1, 2, 2, 1, 0). Reports: [`evidence/wave35-viewstate-outline-level1.md`](evidence/wave35-viewstate-outline-level1.md),
[`-level2`](evidence/wave35-viewstate-outline-level2.md), [`-all`](evidence/wave35-viewstate-outline-all.md),
[`-deep-level1`](evidence/wave35-viewstate-outline-deep-level1.md),
[`-deep-level2`](evidence/wave35-viewstate-outline-deep-level2.md).

### 3.1 What a Show Level changes

Show Level L (1-based) collapses every summary at 0-based level L - 1 and hides every row
at level L or deeper. Rows are the task rows 1..N in file order. The edit changes five
places and nothing else (no task stream, UniqueID or ID moves):

| stream | change |
|---|---|
| `114/TBkndTask/FixedMeta` | byte +15 of each row's 47-byte entry (entry index row + 3, after the 16-byte header): 0x01 shown (the control's value everywhere), 0x03 collapsed summary, 0x00 hidden row |
| `214/CEdl/Var2Data` | the displayed rows (3.2) |
| `214/CEdl/VarMeta` | the Var2Data size word at +0x14 |
| `214/Props` | the same size, the u32 value of the scalar record whose big-endian tag is 0x07000100 (`u32 4, tag, u32 4, value`; offset 11,402 in the measured files) |
| `Props14` | the edit marker |

Measured sets: the five-task base at Level 1 hides UniqueIDs 2 and 3 and collapses 1; the
deep outline at Level 1 hides 2 to 5 and collapses 1 (summary 2 sits under a collapsed row,
so it is hidden, 0x00, not collapsed); at Level 2 it hides 3 and 4 and collapses 2. Level 2
and Show All on the base hide nothing: Project's save differs from its control by the marker
alone (the `-level2` and `-all` reports show no other effect).

### 3.2 The displayed rows (`214/CEdl/Var2Data`)

The stream is a 20-byte header (`u32 len-4`, two `u32 len-8`, format `0x00010000`, a `u32`
item count at offset 16) then items `u32 length, u32 id, u32 kind = 1, payload` (a pad byte
after an odd length); the item list ends exactly at the stream end. Four items depend on the
displayed rows; every other item (including the save-path record `0x26400031`) is copied
byte for byte.

| item | content for N displayed rows, H hidden |
|---|---|
| `0x26400035` | the displayed UniqueIDs, then `0x000ffdc0 - H`, 0, 0 (4 (N + 3) bytes; 4 bytes shorter per hidden row) |
| `0x26400036` | the first displayed UniqueID (4 bytes, unchanged) |
| `0x26400024` | 64 bytes: the displayed UniqueIDs, then `0xffffffff` |
| `0x2640003d` | optional (below): `[N][offsets 0, 22, ... 22 (N - 1)][22 N][0x16][2 zero bytes]`, 4 N + 14 bytes |

**Finding: the optional row-layout record.** Four of the five controls (all but
`-level1`) carry `0x2640003d`. Where it is present, a port that leaves it alone disagrees
with Project by 4 bytes per hidden row (the deep pairs show it). It was verified at N = 6, 5, 4
and 2. The writer rebuilds it where present and never adds it where absent; a layout that is
not the measured one is refused.

### 3.3 The size words, and the wave-33 open gap

**Finding.** The CEdl size words (`214/CEdl/VarMeta` +0x14 and the `214/Props` value) equal
the stream's own length, which includes the save-path record `0x26400031` (the full path of
the saving file). Project's null save and edit save are written under different file names
than the control, so their size words carry the path-length difference as noise. A difference
that crosses a 256 boundary moves byte +21 (VarMeta) and +11,403 (Props) alone; that is the
root cause of the wave-33 open gap recorded as `open_gap_state` in `tests/save_pair_noise.h`
(port 0x02, Project 0x01). The port keeps the control's path record, so its size words are
its own stream's length. The tests normalise Project's null and edit size words to "as if the
control's path record" (`with_control_path_size`) rather than declaring a `KnownGap`; no gap
is claimed for these pairs.

### 3.4 Capability matrix

| shape | state |
|---|---|
| Show Level 1 or 2 on the five-task base (levels 0, 1, 1, 0, 0) | Level 1 enabled; Level 2 **refused** by the edit model (nothing hidden, nothing to persist; the writer reproduces Project's marker-only save and is tested on it) |
| Show Level 1 or 2 on the six-task outline (0, 1, 2, 2, 1, 0) | enabled |
| Show Level 3 and deeper; Show Level 0 or negative | **refused** (unmeasured) |
| Show All Subtasks | session only; withdraws a queued level (the control is already fully expanded; a file that already hides rows is refused) |
| any other task count or level shape; a pending (unsaved) task; the view uid other than 2 | **refused** |
| a file whose FixedMeta flags are not all 0x01 or whose CEdl is not rows 1..N in order | **refused** (replacing a state is unmeasured) |
| combined with another edit, a start-date edit or a table format / formula edit | **refused** (exclusive, in the queue and in the cascade) |

Every refusal is tested with its own needle in both layers (`mppwrite_roundtrip_viewstate_outline`,
`app_edits_show_level`), and the shell queues the level only for these shapes
(`qt_outline_persist`); every other level stays a session collapse with the reason on the
status line.

The reader does not yet restore a persisted collapse on open (the sheet opens fully
expanded); that is a read-side gap, not a write-side one.

### 3.5 Gates

`mppwrite_roundtrip_viewstate_outline` (core: four effect pairs field by field through
`compare_all`, structural checks of the flags, order, copy, layout and size words, the
Show All comparison, dry run and every writer refusal), `app_edits_show_level` (edit model
and cascade against the same pairs) and `qt_outline_persist` (the shell). Mutation checks
and gate logs are recorded in `docs/handoff/wave35-complete.md`.

## 4. Zoom (W35-2.4): DEFERRED with evidence

Pairs (`Application.ZoomTimescale`, each with a null save): `wave35-viewstate-zoom-custom`
(`ZoomTimescale("2w")`), `-custom-10d` (`"10d"`), `-custom-narrow` (`"2w"` again after the
Project window was made 900 wide), `-entire` (Entire Project) and `-reset` (Reset).
Reports: [`evidence/wave35-viewstate-zoom-custom.md`](evidence/wave35-viewstate-zoom-custom.md),
[`-10d`](evidence/wave35-viewstate-zoom-custom-10d.md),
[`-narrow`](evidence/wave35-viewstate-zoom-custom-narrow.md),
[`-entire`](evidence/wave35-viewstate-zoom-entire.md),
[`-reset`](evidence/wave35-viewstate-zoom-reset.md).

### 4.1 What a zoom changes

Each pair changes `214/CV_iew/Var2Data` (83 to 86 effect bytes in 44 runs between offsets
44,854 and 85,125 of the 100,178-byte stream) and the edit marker. Entire Project also
changes eight bytes of `114/TBkndTask/FixedMeta`. `214/CEdl/Var2Data` differs in every
pair, but the control, null and edit saves there differ by the length of the saving
file's path record as in 3.3 (570, 590 and 554 bytes for `-custom`), so it is not read as
an effect of the zoom. No other stream moves.

### 4.2 Why it is not written

The stored words are not a function of the zoom request. The same call, `ZoomTimescale("2w")`,
saved from two Project window widths (the default window and 900 wide), gives two different
saves from the SAME control (the null saves are byte-identical):

| bytes at 44,936 (`214/CV_iew/Var2Data`) | value |
|---|---|
| null save | `00 00 64 00 00 00 40 38 00 00 64 00 …` |
| 2 weeks, default window | `00 00 57 02 00 00 00 48 6e 0d b2 00 …` |
| 2 weeks, window 900 wide | `00 00 ff 01 00 00 40 80 6e 0d 98 00 …` |
| 10 days, default window | `00 00 57 02 00 00 00 48 6e 0d f9 00 …` |
| Entire Project, default window | `00 00 57 02 00 00 40 b4 2b 0d b9 00 …` |
| Reset, default window | `00 00 57 02 00 00 00 48 6e 0d 64 00 …` |

The `u16` at 44,938 (0x0257 = 599 at the default window, 0x01ff = 511 at 900 wide) follows
the saving window's pane width, and the bytes after it (a scaled date word and a trailing
byte) change with both the request and the width. The file does not store the pane width, so
a port cannot derive the value for a given request: it would have to guess the viewport of
a window the file never recorded. Beyond those words, the bytes at 44,948 to 44,958 and the
words at 44,968 to 44,988 (`0x16`, `80 80 80`) are the same in all five pairs and at both
widths, but the five pairs do not cover the rest of the 44 runs, and writing some of the
words while leaving the width-dependent ones at the control's values would not be a port
save that matches Project field by field.

Under the standing rules a command is enabled only for a shape a port save reproduces
field by field. The zoom has one measured value per request at one window width, and the
second width (the `-narrow` pair) shows the value depends on a quantity the file lacks.

### 4.3 Capability matrix

| shape | state |
|---|---|
| any Zoom (Custom, Entire Project, Reset) | **session only**: the shell keeps the timescale zoom for the session; nothing is queued, so File > Save never writes a half-applied zoom |

Pairs still needed to enable it: the pane-width term decoded (several window widths for each
request, the `u16` and the scaled date word expressed from the width and the zoom), or an
oracle that saves at a pinned window width together with a rule the port can satisfy from
the project alone.
